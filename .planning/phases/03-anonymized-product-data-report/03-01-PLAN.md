No new pip or npm packages: Python stdlib only (`argparse`, `csv`, `decimal`, `json`, `os`, `subprocess`, `sys`, `urllib.request`, `urllib.error`, `unittest`), matching the house rule stated in `pull-gsc.py`'s docstring.

    First, `scripts/analytics/research_report.py`, the pure no-network module the tests import by bare name. Module docstring in the `gsc_export.py` style, ending with the stdlib-only line. Constants: `WINDOW_START = "2026-06-01"` and `WINDOW_END = "2026-08-31"` (D-12, fixed calendar months, never a rolling window); `GUILD_FLOOR = 10`; `REPORT_SLUG = "wow-classic-loot-systems-2026"`; `OUTPUT_DIR = "public/research"`; `CSV_HEADER = ["metric_id", "label", "kind", "segment", "value", "display", "denominator", "share_basis", "query_file"]`; and `FORBIDDEN_SQL_TOKENS`, a tuple of lowercase identity tokens the guard rejects: `character_name`, `characters.name`, `guilds.name`, `guild_name`, `player_name`, `.realm`, `battle_net_id`, `user_id`, `discord_server_id`, `created_by`, `awarded_by`, `notes`. Functions:

    `parse_query_header(sql_text)` reads the leading comment block of a query file and returns a dict from the four required keys `metric-id`, `label`, `columns`, `window`, where `columns` is a comma-split list. Raise `ValueError` naming the missing key if any is absent.

    `assert_window_literals(sql_text, path)` raises `ValueError` unless both `WINDOW_START` and `WINDOW_END` appear literally in the SQL body. This is the D-12 reproducibility guard and it is the reason no date is ever interpolated into SQL at run time.

    `assert_no_forbidden_columns(sql_text, path)` lowercases the SQL and raises `ValueError` naming the offending token if any entry of `FORBIDDEN_SQL_TOKENS` appears. `expansions.name` and `raid_tiers.name` must pass, because D-14 groups expansions by name text.

    `apply_floor(segment_counts, floor=GUILD_FLOOR)` is the single centralized k-anonymity function, per RESEARCH.md's Don't-Hand-Roll table: it must be the only place a floor comparison lives. Segments at or above the floor are kept verbatim; segments below it accumulate into one `Other` entry. If the accumulated `Other` is nonzero but itself below the floor, return the module's `WITHHELD` sentinel instead of a dict, so the caller routes the whole breakdown to `unavailable` rather than publishing a small cohort under a different label. An empty input returns an empty dict with no `Other` key.

    `quantize_display(value, kind)` is the precision contract. For `kind` in `percentage` and `median`, quantize with `decimal.Decimal(str(value)).quantize(Decimal("0.1"), rounding=ROUND_HALF_UP)` and return the string, suffixing `%` only in the page layer, not here. For `kind == "count"` return the integer as a string with no decimal point. Do not call the builtin `round`: it is banker's rounding and would render a 2.25 median as 2.2.

    `build_artifact(window, definitions, sample, findings, unavailable, generated_at)` returns the artifact dict in this exact shape, which is the D-05 contract: top-level keys `report_slug`, `window` (with `start` and `end`), `generated_at`, `guild_floor`, `definitions`, `sample`, `findings`, `unavailable`. `sample` holds `active_guilds`, `raid_events`, `loot_awards`, `raiders_with_approved_lists`. Each `findings` entry holds `metric_id`, `label`, `kind`, `value` (unrounded, as returned by Postgres), `display` (the quantized string), `denominator`, `share_basis`, `sums_to_100`, `segments` (a list of objects with `segment`, `guild_count`, `share`, `display`), `floor_applied`, and `query_file`. Each `unavailable` entry holds `metric_id`, `label`, and `reason`. Set `sums_to_100` false for any breakdown whose segment guild counts sum above `sample.active_guilds`, which is the D-14 multi-bucket case.

    `write_json(artifact, path)` writes with `indent=2`, `sort_keys=False`, and a trailing newline so the committed file diffs cleanly. `write_csv(artifact, path)` writes `CSV_HEADER` then one row per sample number (metric_id `sample.active_guilds` and its three siblings), then one row per finding, then one row per segment of that finding, in the order stated in the behavior block, always through `csv.writer` and never a manual comma join: the RUNBOOK documents a real comma-corruption incident in this directory. `resolve_output_path(path)` reuses `gsc_export.resolve_export_path`'s guard shape with `OUTPUT_DIR` as the default parent.

    Third, `scripts/analytics/queries/wow-classic-loot-systems-2026/01-sample-definition.sql`. Header comment block declaring `metric-id: sample-definition`, `label:`, `columns: active_guilds,raid_events,loot_awards,raiders_with_approved_lists`, and `window: 2026-06-01..2026-08-31`. Body: a CTE named `active_guilds` implementing the D-13 OR-definition over `guilds`, where a guild qualifies if it has at least one `raid_events` row with `guild_id` matching, `raid_date` inside the window, and `is_skipped` not true; OR at least one `loot_history` row with `guild_id` matching and `awarded_date` inside the window; OR at least five `loot_submissions` rows with `guild_id` matching, `status = 'approved'`, and `COALESCE(reviewed_at, submitted_at)` inside the window. Every upper bound is written as a comparison strictly less than `DATE '2026-08-31' + INTERVAL '1 day'`, which is correct for both date and timestamp columns and keeps the `2026-08-31` literal in the text for the window guard; every lower bound is greater than or equal to `DATE '2026-06-01'`. Filter out rows whose `guild_id` is null. Then three further CTEs restricted to the active cohort: the non-skipped `raid_events` count in the window, the `loot_history` count in the window, and the count of distinct `loot_submissions.character_id` where `status = 'approved'` and the window predicate holds (D-15, a character count with no alt de-duplication through `character_aliases`). <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Committed `.sql` file to production Postgres | The Management API `/database/query` endpoint runs arbitrary SQL as a superuser-equivalent connection with Row Level Security bypassed entirely. Anything that reaches this boundary executes. |
| Production row data to committed artifact | The runner is the only gate between per-row production data (which includes guild names, character names, and realms) and a file that is committed, deployed, and publicly downloadable. |
| macOS Keychain to process environment | A personal access token capable of dropping tables enters a Python process that also writes files and prints to a console a human reads. |
| Committed artifact to public web | Everything under `public/` is served verbatim and auto-deploys from main about 12 seconds after merge. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Information Disclosure | Identity columns reaching the artifact, the console, or the page through a query's SELECT list | high | mitigate | `assert_no_forbidden_columns` rejects any query text containing an identity token before execution, and `run_sql` asserts the response column set equals the header's declared `columns`. Both run on every normal run, not only under `--lint-queries`. Acceptance criteria prove the guard rejects a `character_name` select. |
| T-03-02 | Information Disclosure | Re-identification of a single guild through a small segment | high | mitigate | `apply_floor` is the single centralized floor check; segments below 10 merge into `Other`, and a sub-floor `Other` withholds the entire breakdown instead of publishing it. No cross-tabulated segment is produced anywhere in this phase. |
| T-03-03 | Information Disclosure | `SUPABASE_ACCESS_TOKEN` leaking into stdout, the artifact, a commit, or checkpoint output | high | mitigate | Token is read from the Keychain at run time only, is never printed, never written to a file, and never placed in a URL. The error path reports the HTTP status and response body without request headers. An acceptance criterion greps the diff for an `sbp_` prefix. |
| T-03-04 | Tampering | Arbitrary or mutating SQL reaching production through the runner | high | mitigate | The runner posts only the verbatim text of a committed `.sql` file; no statement is assembled from a variable.
