## Investigation findings (verified in WT at f475b60e)

1. Route. GET (ids as a comma-separated query value) and POST ({ ids }) call getItemCounts with the service-role client after getAuthenticatedUser only: no guild, membership or ownership check, and no limit on ids. 2. What is returned. For each list id supplied, the number of live items on that list, in any guild; a key's presence also shows the list exists and has items. No item names, ranks or owners. List ids are random UUIDs, so a caller needs an id from somewhere else.
3. What RLS already allows. loot_submission_items has one SELECT policy, loot_submission_items_select: an active membership in the list's guild. loot_submissions has three SELECT policies: loot_submissions_select (active member), "Guild members can view guild submissions" (any membership row in the guild, active or not) and "Users can view own character submissions". A planner PGlite probe (scratchpad, deleted after use) at f475b60e: for O_A, R1, R2, GONE, RB, GM_A and GM_B the D-01 rule's counts equal what each user's own session reads from loot_submission_items (removed items excluded, drafts included); GONE (inactive) reads no item rows but reads the former guild's loot_submissions rows (follow-up FU-1).
4. Callers. Only LootSubmissionsContent.tsx (POST, at initial load and in loadSubmissions). The page redirects users without manage_submissions to /overview, reads the lists with the browser client filtered to activeGuild.id, and activeGuild comes from the user bundle, which lists active memberships only (lib/cache/user-bundle.ts, eq is_active true). Every id it sends is therefore a list in a guild where the caller is an active member, so D-01 changes nothing on the page. A non-OK response gives each list 0 items. The GET handler has no caller; LootSettingsContent.tsx only mentions the route in a comment.
