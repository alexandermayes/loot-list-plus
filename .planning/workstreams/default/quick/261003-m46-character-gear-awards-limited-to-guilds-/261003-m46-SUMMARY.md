# Quick Task 261003-m46: Character gear awards limited to shared guilds, officer check by role position Summary

**GET /api/character-gear now limits a non-owner's loot-history awards to the guilds they actively share with the character, and POST now recognises officers through verifyOfficerPermissions (role position or guild creator) instead of two hardcoded role names, closing a cross-guild read and a role-name bypass on a service-role route with 29 new tests and a PGlite mirror check.**

## Task Commits

All work was committed in a dedicated worktree on branch `fix/character-gear-shared-guild-awards` (branched from `origin/main` at `1a0e6473`):

1. **Task 1 (tracer): GET award filter, tests**: `b70b05e3` (fix)
   - `awardGuildIds` computed from the caller's active memberships in the character's active guilds (null for the owner, meaning no filter); the `loot_history` query adds `in('guild_id', awardGuildIds)` only for a non-owner
   - Removed the unused `EquippedItem` interface (the directory's one pre-existing eslint warning)
   - 13 new tests: 401/400/404, owner (every guild, no membership read), shared guild (one guild), multi-guild with de-duplication, four refusal cases, three fail-closed cases
2. **Task 2 (TDD): POST officer check by role position, tests**: `803c1adb` (fix)
   - Replaced the caller-characters read and the two-role-name membership read with a loop over the character's active guilds calling `verifyOfficerPermissions` (imported from `@/utils/server-roles`), stopping at the first `hasPermission: true`
   - 16 new tests: owner import (delete + insert, 3 items), parse-error path, a custom officer role name (Raid Leader, position 60), the default Officer role, the guild creator with no membership in that guild, six refusal cases (Member, Veteran, a role literally named "Officer" below officer position, an inactive officer, an officer of a guild the character is inactive in, an officer asking about a character with no active membership anywhere), and one fail-closed case

## What each test proves before and after the change

**GET (Task 1).** Before the change, a non-owner viewer with only one guild in common with the character still saw every award the character had ever received, across every guild. The two new shared-guild and multi-guild tests failed against the unmodified route (confirmed by running them first) and pass after the `awardGuildIds` filter was added. The owner's path, every refusal case, and the three fail-closed cases (membership read error, loot_history read error, equipped-items read error) were already correct and stayed green throughout.

**POST (Task 2).** Before the change, the officer check matched only the two literal role names `'Officer'` and `'Guild Master'`, regardless of a guild's actual `guild_roles` position table. Two cases proved this directly by running them before the route change: a custom role named "Raid Leader" at position 60 was refused (expected to be accepted after the fix), and a role named "Officer" that a guild had repositioned to 10 (below officer level) was accepted (expected to be refused after the fix). The guild-creator case also failed before the fix, since the old check had no creator fallback at all. After swapping to `verifyOfficerPermissions`, all three match the database's `is_guild_officer` rule.
