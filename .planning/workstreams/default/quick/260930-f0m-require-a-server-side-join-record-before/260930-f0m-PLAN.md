<objective>
Require a server-side join record before a character is added to a guild.

Purpose: since 20260930000100, membership rows are written only by the server. The legitimate joins each prove the right to join on the server: an invite code (redeem_invite_code), a verified Discord server membership, or guild creation (guilds.created_by, which is server-managed since 20260930000100). Two service-role routes add a character to a guild afterwards, POST /api/characters/[id]/guilds and POST /api/battlenet/characters/import, and they check only character ownership. When a user joins before they have a character, the only trace of the join today is user_active_characters, which the user's own session can write. After this change a character is added to a guild only through a join the server recorded: the invite and Discord routes write a join record when the user has no character yet, and the two routes accept a guild only for its creator, for a user who already has another active character in it (alts), or for a user holding that record.

Output: one migration (service-role-only table plus the OD-1 backfill) and its shape test, a small server-only helper with unit tests, changes to four routes with route tests, and a scratchpad-only PGlite proof. Local commits only in WT; the orchestrator reviews, pushes and opens the PR.

Constraints: "guild_join_grants_pkey" PRIMARY KEY ("user_id", "guild_id") (one row per user and guild; a new join upserts it and starts a fresh window); "guild_join_grants_source_check" CHECK ("source" IN ('invite_code', 'discord_verify', 'backfill')); "guild_join_grants_expires_check" CHECK ("expires_at" > "created_at"); "guild_join_grants_user_id_fkey" FOREIGN KEY ("user_id") REFERENCES "auth"."users"("id") ON DELETE CASCADE; "guild_join_grants_guild_id_fkey" FOREIGN KEY ("guild_id") REFERENCES "public"."guilds"("id") ON DELETE CASCADE. - D-03 (access): RLS enabled and no policies, so a client role sees and writes no rows even if a privilege were granted later; plus REVOKE ALL FROM PUBLIC, anon, authenticated, because the baseline default privileges (baseline lines 4849-4852, and Supabase in production) give anon and authenticated ALL on every new public table. GRANT ALL TO service_role re-asserts the default. - D-04 (access rule): resolveGuildJoinAccess(service, { userId, guildId, excludeCharacterId?, now? }) returns { allowed: true, via: 'creator' } when guilds.created_by equals userId; else { allowed: true, via: 'member' } when any character the user owns (other than excludeCharacterId) has a character_guild_memberships row in the guild with is_active true; else { allowed: true, via: 'grant' } when the user's guild_join_grants row for the guild has consumed_at null and expires_at later than now; else { allowed: false }. A guild that does not exist resolves as not allowed, so the 403 does not say whether the guild exists. Any lookup error throws an Error with a constant message; callers let their existing catch return 500 'Internal server error' with no write (fail closed). In POST /api/characters/[id]/guilds the check runs after the existing lookups and the existing 409 for an active membership, and before the insert or reactivation, with excludeCharacterId set to the route's character id. Not allowed: status 403, body { error: 'You are not a member of this guild' } (D-09), no write of any kind. Role assignment is unchanged (Guild Master for the creator, otherwise getDefaultRoleName, per 260929-qzn D-08).
- D-05 (use once): after each successful membership write that leaves the user active in guild G, the route calls consumeGuildJoinGrant(service, { userId, guildId }), which runs UPDATE guild_join_grants SET consumed_at = now WHERE user_id = userId AND guild_id = G AND consumed_at IS NULL. It is called whichever path allowed the write, so a creator or member who also holds a record uses it up too. Call sites: characters route insert and reactivation; import upsert when it succeeded; invite insert and reactivation; Discord insert and reactivation. Not called when the membership write failed, and not in the Discord "Already a member" branch (no membership write). A consume error is logged with a constant message and does not change the response (the membership is already written). Why: after a kick (MemberManager removes all of the member's characters and says "They can rejoin with an invite code.") or a leave, the user has no active membership and no usable record, so only a new invite or Discord join lets them add a character again.

1. Every path that adds or reactivates a membership (wide scan of every .from('character_guild_memberships') insert, upsert and is_active true update in app, lib, utils, domain, discord-bot and companion, plus every SQL function in the migrations):

| POST /api/guild-invites/[code] | redeem_invite_code (user session, claims one use atomically) | with a configured character: insert or reactivate the main (default role, trial fields, joined_via 'invite_code'); without: only user_active_characters (null character, guild) and needs_character_creation |

| scripts/*, app/api/admin/clear-all-guilds | dev and admin service role | not affected |

No SQL function, cron, bot, companion or client component inserts or reactivates memberships.

2. UI flows that call the two routes:
- CreateCharacterModal: after POST /api/characters, POSTs /api/characters/[id]/guilds with guild_id = activeGuild.id (or a sessionStorage key pending_guild_join that nothing sets) and joined_via 'manual'; a non-ok answer is only logged, then the page reloads. Its Battle.net tab opens BattlenetCharacterPickerModal.
- CharacterSelector handleAddToGuild: adds an existing alt to the active guild (the user is already a member there); shows data.error on failure.
- BattlenetCharacterPickerModal (from CreateCharacterModal, EditCharacterModal and the character edit page): sends guildId = activeGuild?.id; shows data.error on failure.
- LoginPage (invite) and guild-select/discord-join redirect to /overview?create_character=true on needs_character_creation, and show data.error on failure.
- GuildContext shows the pending guild from user_active_characters only when the user has no characters at all; when the user has characters but no membership in that guild it clears active_guild_id. So in the UI the join record path is used only for the first character after a no-character join; later characters use the member path.
- Switching characters (PUT /api/user/active-character) writes only user_active_characters and, when a character is given, requires its active membership in the guild. No membership write.

3. user_active_characters: the user's own session may insert, update, delete and read its row (policies at baseline 3783, 3805, 3848, 3895; ALL granted to anon and authenticated at 4811-4813). It is written by the join routes, guild creation, leave, guild delete, character delete, the active-guild and active-character routes, the auth callback, and GuildContext directly from the browser; PUT /api/user/active-character accepts a guild_id with no membership check when no character_id is sent. No policy, SQL function or route uses it to authorize anything; it is UI state. It stays that way (D-12).

4. No existing table records a user-level join: guild_invite_codes counts uses (current_uses) but not who redeemed; audit_logs records officer actions, not joins; the PostHog guild_joined event is external; profiles and user_preferences hold no guild. A new table is needed. Guilds are world-readable (baseline 3588), so nothing new is revealed by the pending-guild display.

5. Where to write the record: the invite route right after redeem_invite_code succeeds and the no-character branch is chosen, and the Discord route right after the Discord server check passes, in its no-character branch; both already hold a service-role client. Creators need no row (D-10). A 30-day window covers a user who joins and comes back later to make a character; after the first character the member path takes over.

6. Precedent and types: 20260928180000_create_addon_auth_codes.sql is a service-role-only table (RLS on, no policies, REVOKE ALL FROM anon, authenticated, GRANT ALL TO service_role) with a shape test. createServiceRoleClient() builds an untyped client, so lib/database.types.ts needs no change (addon_auth_codes is not in it either). The baseline default privileges grant ALL on new public tables to anon and authenticated, so the REVOKE is needed next to RLS.

7. Existing approved copy that fits: 'You are not a member of this guild' (403 in app/api/user/active-guild/route.ts; 404 in app/api/guilds/leave/route.ts), and "Couldn't join guild. Try again or contact an officer." (500 in both join routes).

8. Related items noted, not changed here (SUMMARY follow-ups): the no-character path skips new_members_start_as_trial (OD-3 decides); a guild creator who imports their first character through Battle.net gets the default role instead of Guild Master; CreateCharacterModal only logs a failed guild attach; an alt added through the member path gets full status even when the user's other character is on trial; CreateCharacterModal reads a pending_guild_join key that nothing sets.
