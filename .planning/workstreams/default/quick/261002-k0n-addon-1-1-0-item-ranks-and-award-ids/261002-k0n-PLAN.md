## Design decisions (planner; referenced by ID in the tasks)
- D-01 (OD-3, port): copy origin/main:addon/LootListPlus/Modules/ScoreEngine.lua from WT over ADDON/Modules/ScoreEngine.lua byte for byte (git show into the file, then cmp). Commit it alone as commit A1 "Port the web-parity ScoreEngine from the LootList+ repo"; the body names source commit 8d81b1dc and lists 3a4b1995, 8c74a2af, e7c57b6f, a50aaabb, f1b1e29e, 30a7422b and 6089e0d8 with one line each on what they added (from finding 2).
- D-02 (OD-7, tests): plain Lua 5.1 tests under tests/, run as luajit tests/run.lua from the addon repo root.
  - tests/run.lua keeps an explicit list of test files (luajit has no directory listing). Each test file returns a table of named test functions. The runner calls each with a fresh harness, prints PASS, FAIL (with the message) or KNOWN GAP lines and a count line, and exits 1 when any test fails or no test ran. --selftest-fail runs one built-in failing test and must exit 1. --print-award-ids prints 20 ids from LD:NewAwardId for one fixed awardedAt (added in Task 2).
  - tests/harness.lua sets the WoW stubs (GetBuildInfo returning interface 11508, IsInRaid false, SendChatMessage and GetLootMethod no-ops returning non-master loot, date wrapping os.date with an optional fixed clock), loads LibDeflate from Libs/LibDeflate/LibDeflate.lua before defining a LibStub stub that returns it, then loads Core/Constants.lua, Core/VersionCompat.lua, Core/Utils.lua, Core/DB.lua, Modules/ScoreEngine.lua, Modules/Sync.lua and Modules/LootDistribution.lua (in .toc order) into a new LLP table, with recorder stubs for LLP.addon (Print, Debug) and LLP.LootFrame (Show, RefreshItem, RefreshAll). DB.profile is a deep copy of DB.defaults.profile (DB:Init needs AceDB). Helpers: fixed clock, import string builder (JSON text through LibDeflate CompressDeflate, Sync:EncodeBase64 and the LLP1:1: prefix), export decoder (prefix strip, Sync:DecodeBase64, DecompressDeflate, Sync:ParseJSON), JSON fixture reader through Sync:ParseJSON, a serializer that writes DB.profile as Lua source and a reload helper that loads that source into a freshly loaded LLP (simulates /reload), and eq, near and truthy assertions with messages.
  - The test code and every changed addon file use Lua 5.1 syntax only, since WoW runs Lua 5.1: no labels or jump statements, no integer division or bitwise operators, no LuaJIT-only libraries. Addon files (outside tests/) also never load modules through the module loader, since WoW has none. The Task 2 and Task 3 verify chains enforce this on added lines outside tests/. They also run a stock Lua 5.1 compiler in parse-only mode (luac5.1 -p) on the changed addon files when one is already on the machine; none was found on 2026-10-02, and none is to be installed.
  - The harness never calls math.randomseed. In WoW, math.random is backed by a secure random source and addons never seed it. LuaJIT's unseeded generator still gives distinct successive values, so A2's uniqueness check holds as written.
- D-03 (web parity fixtures): tests/tools/gen_web_fixtures.mts is committed in the addon repo and run from a LootList+ checkout: cd into the checkout, then LLP_REPO="$PWD" npx tsx ADDON/tests/tools/gen_web_fixtures.mts ADDON/tests/fixtures.
  - It dynamically imports, through pathToFileURL, LLP_REPO/domain/scoring/index.ts (computeScore, calculateAttendanceScore, calculateLootScore, resolveActiveRaiderModifiers), LLP_REPO/domain/scoring/__tests__/fixtures.ts (record helpers, settings presets, LOOT_SCORE_FIXTURES) and LLP_REPO/lib/addon/member-ranked-items.ts (buildMemberRankedItems). It fails with a clear message when LLP_REPO is unset.
  - It writes tests/fixtures/web_scoring.json: generatedFrom (the LootList+ commit sha only, from git rev-parse in LLP_REPO, no local paths), asOfDate fixed at 2026-09-20, attendanceCases (records, totalRaids, settings, expected from calculateAttendanceScore), lootScoreCases (LOOT_SCORE_FIXTURES with expected from calculateLootScore), and scoreCases. Each score case is an import payload in the server's export shape (guildId, settings with single_raider_modifiers already resolved by resolveActiveRaiderModifiers for asOfDate, items, members with items arrays, priorities keyed by loot item id, blp, attendance keyed by character id with records and totalRaids) plus, per character, the expected total from computeScore (specRoles = [role], guildRank = guild_role, donationBonus 0, the unresolved raider entries in config, asOfDate) and the expected order (total descending, higher rank first on a tie). Synthetic names and ids only, ASCII only.
  - It writes tests/fixtures/export_string_ranks.txt: one LLP1:1: line built exactly as GET /api/addon/export-string does (JSON.stringify of the payload, node:zlib deflateRawSync, base64), whose members[].items come from buildMemberRankedItems over synthetic submissions: Thrall lists 20928 at ranks 30 (slot 1) and 50 (slot 2), a removed 20928 row at rank 60, and 19019 at rank 10; Jaina lists 20928 at 40; Sylvanas lists 20928 at 45 and 20 and has one received copy (counts map entry for her id and 20928).
  - Output is deterministic: JSON.stringify with two-space indent and a trailing newline. Score case coverage: points-per-raid defaults with explicit rank_modifiers; late, benched, excused, no-call-no-show and points_override records; linear with signups; breakpoint at each threshold with excused records shrinking the denominator; role bonus on; raider bonus on with a permanent entry, an entry active on asOfDate and an ended entry; role, spec and character item priorities; bad luck on below and above the cap; trial penalty on; and two raiders tied on total with different ranks.
  - Known-gap rule: if a generated case fails against the ported engine, ScoreEngine.lua is NOT changed. The executor moves that case into a knownGaps list in the generator (still generated; the runner prints KNOWN GAP and does not fail), and records the case and the web commit that introduced the rule in the SUMMARY as an open question.
- D-04 (ranks shape): Sync:ProcessImport collects every { wowhead_id, rank } of a member (entries without both are skipped), sorts each item's ranks highest first (equal ranks in two slots stay as two entries) and writes items[tostring(id)] = the highest rank and itemRanks[tostring(id)] = the sorted array. This is the shape companion 1.1.0's convertMembersToLuaFormat writes, and it no longer depends on the server's row order.
- D-05 (OD-2, counts): DB:GetAwardCount(characterId, wowheadId) returns profile.guildData.awardCounts[characterId][tostring(wowheadId)] or 0. DB:IncrementAwardCount(characterId, wowheadId) adds 1, creating the tables on demand, and does nothing unless DB:HasGuildData() is true and both arguments are set. That guard means a reset profile, which points at DB.defaults.profile.guildData, is never written into. awardCounts is not added to DB.defaults: SetGuildData replaces guildData wholesale, so every import (/llp import, or the companion's guildData write) resets the counts, and the table lives in the profile, so it survives /reload. The defaults comment block documents awardCounts, members' itemRanks and pending awards' awardId.
- D-06 (current rank): SE:GetCurrentItemRank(characterId, member, wowheadId) uses member.itemRanks[key] when it is a non-empty table, otherwise { member.items[key] } when that is a number, otherwise returns nil. It returns ranks[DB:GetAwardCount(characterId, wowheadId) + 1] only when that value is a number, so a hand-edited SavedVariables value can never reach the score arithmetic. CalculateCharacterItemScore calls it in place of the member.items lookup; nothing else in the engine changes, so the Task 1 parity tests keep passing unchanged.
- D-07 (award id): LD:NewAwardId(awardedAt, slotIndex) returns awardedAt .. "-" .. the integer slot (math.floor(tonumber(slotIndex) or 0)) .. "-" .. string.format("%06x", math.random(0, 16777215)). That is at most about 32 characters, and it matches the server's AWARD_ID because awardedAt starts with a digit and uses only digits, '-', ':', 'T' and 'Z'. AwardItem and ManualAward each read U:GetTimestamp() once into a local and set both awardedAt and awardId on the record, which goes to pendingAwards (exported by the unchanged Sync:ToJSON) and lootHistory. Comms:BroadcastAward is unchanged. Two copies in one loot window differ by slot; awards from two corpses in the same second differ by the random part, and even a collision would need the same item, the same raider and the same second (the server key embeds both).
