<objective>
Follow-up FU-1 to GH #331 and #293 (PR #337, merged as 08dd6fb6): a raider who listed an item twice (AQ40 Qiraji Bindings, one 'Shared Boss Loot' loot_items row that several bosses drop) must be able to win it twice on one raid night. Today idx_loot_history_unique_award (baseline line 2822) blocks the second award: the web bulk route maps the 23505 to 'duplicate' (and the master sheet modal then shows a success toast anyway, because it only checks res.ok), and the addon paths treat it as already recorded (#295/#307, PR #322). The index is also the retry guard for the addon paths, so it is replaced by an explicit copy number plus a per-award idempotency key, not just relaxed.

Purpose: officers can record what really dropped, retries and re-imports still never create duplicate awards, and the deploy is safe on the live table.

Output: one migration (its own commit), a pure copy helper, a rewritten addon insert helper with a keyed path, import-string, bulk (POST and PATCH), loot-award and award-modal changes, tests, a PGlite proof in SCRATCH, and three or four commits on fix/second-same-night-award. The in-game part (companion and addon releases) is a separate follow-up plan, written out at the end of this objective. No push, no PR.

## Investigation findings (planner, 2026-10-01, from origin/main 2d668d01 and the private addon repo)

Every path that inserts loot_history, and what it relies on the unique index for:
- POST /api/loot-history/bulk (route.ts lines 226-282): one insert per item; 23505 becomes results[i].error 'duplicate'. Callers: master sheet ItemCandidateModal (one item, raid_event_id = mostRecentRaidEventId; double-submit guard and "already got it tonight" guard) and raid-tracking Gargul import, two code paths (_client.tsx about 1800-1845 and 2055-2105; re-paste guard: lines are DATE;[ITEM_ID];NAME with a date and no time, and a fresh import relies on 23505 for "{name} already has that item" and "{name}: Already received {item}"; edit mode deletes the night's loot first).
- PATCH /api/loot-history/bulk (reassign, raid-tracking reassignLoot): an update of character_id; 23505 today surfaces as a 500 with the raw Postgres message.
- POST /api/addon/loot-award (companion, one award per request): body has only awarded_date (the companion's readPendingFromSavedVars splits awardedAt at 'T'), so a re-send and a second copy are identical requests. insertAddonAward treats 23505 as already_recorded; the companion re-sends routinely (it clears SavedVariables pending, but the running addon rewrites its in-memory pendingAwards on logout).
- POST /api/addon/import-string (addon export string LLP1E:1): awards carry wowheadId, lootItemId, characterId, characterName, awardedAt (UTC ISO to the second, Core/Utils.lua GetTimestamp), manual. The export is cumulative until the officer clicks "Clear pending" in the addon (Modules/Sync.lua EncodeExportString sends profile.pendingAwards; UI/ImportExportFrame.lua offers Clear pending after a paste), so exports can be cumulative or incremental. insertAddonAward: 23505 means already_recorded; unmatched names use a same-night same-name pre-check.
- remove-item "obtained outside of raid" path: inserts with no raid_event_id, never touched by the index. scripts (seed, purge, link-loot-to-raids, backfill-team-event-routing) are one-off; see FU-T5. No SQL function or ON CONFLICT names the index. No other unique index on loot_history besides the primary key.

Per-award identity available per source (the idempotency key):
- Web modal: the officer's intent. Copy n of (night, raider, item) is the key: a first award is copy 1; a deliberate second award is sent as copy next_award_copy after the C-1 prompt, so any resend of the same intent carries the same n.
- Gargul paste: no timestamp, so the n-th identical line of one paste is copy n.
- Addon (export string now, companion later): addonAwardKey = 'addon:' + awardedAt + ':' + wowheadId + ':' + lower(trim(characterName)). The same in-game award yields the same key from the export string and from a companion that forwards awardedAt, so the two paths dedupe against each other. Limitation: two awards of one item to one raider in the same second share a key (the follow-up addon release adds an awardId).

Create both before dropping the old one.
- D-02: production safety: one migration file, statements idempotent (IF NOT EXISTS / IF EXISTS), SET LOCAL lock_timeout of 5s first, plain index builds (deploy-migrations.sh sends the whole file as one Management API query, an implicit transaction in which the concurrent build option is rejected; loot_history is small, so the brief write lock is acceptable; if the API ever ran the statements one at a time instead, the IF NOT EXISTS / IF EXISTS forms still let a re-run finish the file, and the new indexes exist before the old one goes). No backfill (no awarded timestamps were ever stored, so keys cannot be derived; the claim rule in D-04 handles legacy rows). No new function or trigger, so the function-grants ratchet has nothing to check.
- D-03: addonAwardKey is the addon identity (format above). It returns null unless awardedAt is a string matching the addon's UTC ISO format (YYYY-MM-DDTHH:MM:SS with optional fraction, ending in Z), wowheadId is a positive integer, the trimmed name is non-empty, and the whole key is at most 200 characters.
- D-04: keyed addon insert (insertAddonAward when row.source_award_key is set): (1) a row with this key in this guild means already_recorded; (2) on a linked night, an unkeyed row for the same item, night and raider (same character_id, or for an unmatched name a null character_id with the same trimmed lowercased name) is claimed by stamping the key on it with an UPDATE guarded by source_award_key IS NULL, and the award is already_recorded; a lost claim race loops; (3) otherwise insert with award_copy = highest existing copy for (guild, item, raider, night) + 1 (1 when unlinked or unmatched name) and the key; a 23505 loops back to step 1 (an identical concurrent retry is then found by key; a different concurrent award recomputes the copy); at most 3 attempts, then throw; a next copy above 10 throws. The keyless path (no source_award_key) keeps today's exact queries and results.
- D-05: web modal: first award sends no award_copy (copy 1). A 'duplicate' result with a numeric next_award_copy opens the C-1 prompt with button C-2; confirming re-sends the same award with award_copy = next_award_copy. A 'duplicate' with next_award_copy null (10 copies already) shows C-3 as an error toast. A non-duplicate per-item failure shows the existing 'Failed to award: {message}' toast. Success keeps the existing toast.
- D-06: bulk POST: optional per-item award_copy, validated (integer 1 to 10, else 400 with C-4 and invalid_award_copy_indexes before any write); items without one are numbered by assignAwardCopies after routeRecordsToTeamEvents; unlinked or characterless items are always copy 1; a 23505 on a linked item returns { index, success: false, error: 'duplicate', next_award_copy } (number, or null at the cap; key omitted if the lookup itself failed).
- D-07: bulk PATCH: when character_id changes to a different non-null raider on a linked row, the update also sets award_copy to that raider's next free copy for the row's item and night (left unchanged if the cap is hit, so the database decides).
- D-08: loot-award: optional awarded_at feeds addonAwardKey; invalid or absent means keyless (today's behavior). awarded_date handling is unchanged.
- D-09: BLP, apply-receive-skip, master sheet counts, loot history views, Discord announcements and audit logs need no code change (one row per award already; per-night BLP semantics already right).
