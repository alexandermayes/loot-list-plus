# Phase quick-261001-t74: Fix flaky fetch-unstub-teardown-order Summary

**Fixed the PR #337 CI flake by reordering test teardown in two files (RTL cleanup() before vi.unstubAllGlobals()), proven by a deterministic regression test that reproduces the exact CI error under the old order and passes cleanly under the new one across 32 repeated/shuffled/load runs.**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2
- **Files modified:** 2
- **Commits:** 2 (local, unpushed, on `fix/flaky-fetch-unstub-order`)

## Verified Diagnosis

PR #337's CI run (Test job attempt 1, run 36962096163, job 110697784310) passed all 159 files / 2791 tests but vitest exited 1 on an unhandled rejection: `TypeError: Failed to parse URL from /api/reserve-runs/items?raid_tier_id=t1` at `CreateReserveRunModal.tsx:182`. The re-run passed.

Root cause: vitest runs a describe-level `afterEach` (in the test file, `vi.unstubAllGlobals()`) **before** the root-level `afterEach` registered in `vitest.setup.ts` (RTL `cleanup()`). Between the two, the component is still mounted with the real fetch restored. When `cleanup()` then unmounts, React first flushes any pending passive effects. If a tier-selection commit landed but its passive "load items when tier changes" effect hadn't yet run (the scheduler yields when a commit task exceeds its 5ms slice, more likely on a loaded CI runner), the unmount itself fires the items effect, which calls the real `fetch` with a relative URL. Node's fetch rejects ("Invalid URL"); `load()` has no catch; vitest reports an unhandled rejection.

App code is not at fault: a relative fetch URL resolves fine against the page origin in a browser; only Node's fetch in jsdom tests rejects it, and only because test teardown hands the still-mounted component the real fetch. `CreateReserveRunModal.tsx` was not modified.

## What the Final Regression Test Asserts

Kept as designed (never needed to be weakened — see Key Decisions): the test arms a slow-tier-render `getRaidIcon` mock for a single tier name, renders the modal, waits via a `MutationObserver` (not `findByText`/`waitFor`, which drain through a `setTimeout(0)` that could let the pending effect race ahead and make the guard non-deterministic) for the tier text to appear, then:

1. Asserts the stubbed fetch has **NOT** been called with `/api/reserve-runs/items?raid_tier_id=t1` (proves the "load items when tier changes" effect is genuinely still pending — this is the precondition that makes the test exercise the real race, not a no-op).
2. Calls `teardown()` (the same function the file's `afterEach` runs).
3. Asserts the stubbed fetch **HAS** been called with that same URL (proves the unmount flushed the pending effect while the stub was still installed, so the real fetch was never reached).

Across all 32 runs under plain, shuffled, repeated, and concurrently-loaded conditions, assertion 1 never failed, so the orchestrator's drop-if-flaky instruction did not trigger — the precondition assertion and the busy-wait mock that supports it were both kept as written in the plan.
