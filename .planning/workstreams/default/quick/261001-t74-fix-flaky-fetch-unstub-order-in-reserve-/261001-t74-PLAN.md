The re-run passed.

Verified diagnosis (planner, 2026-10-01):
- The CI log says the error originated in CreateReserveRunModal.test.tsx. The URL carries raid_tier_id=t1, which only test 2 ("Forever guild with a raid tier") produces; vitest attributed it to test 3 only because the rejection surfaced asynchronously after test 2's teardown.
- vitest runs the describe-level afterEach (vi.unstubAllGlobals(), restoring Node's real fetch) BEFORE the root-level afterEach registered by vitest.setup.ts (RTL cleanup()). Between the two, the component is still mounted.
- Sharper than "a window of time": when cleanup() unmounts, React first flushes any pending passive effects. If test 2's tier commit landed but its passive effect had not yet run (the scheduler yields when a commit task exceeds its 5ms slice, which happens on a loaded CI runner), the unmount itself runs the items effect, which calls the real fetch with a relative URL. Node's fetch rejects ("Invalid URL"), load() has no catch, and vitest reports an unhandled rejection.
- Reproduced deterministically by the planner in a scratch copy: forcing the tier commit past the slice (busy-wait inside getRaidIcon, which the component calls while rendering the selected tier) and ending the test on the MutationObserver microtask gave the exact CI error 5 out of 5 runs with the old teardown order, and 5 out of 5 clean passes with cleanup() first.
- Correction to the task description: SetupGuide.tsx does NOT render CreateReserveRunModal (its test file only mentions it in a comment). SetupGuide has its own fetch effect (checkSetupProgress calls fetch('/api/guild-invites?guild_id=...') from a useEffect) and the same unstub-before-unmount afterEach, so it is a latent instance of the same hazard. There the rejection would be caught by checkSetupProgress's try/catch and logged as a console error, so it cannot fail CI today, but it gets the same ordering fix.
