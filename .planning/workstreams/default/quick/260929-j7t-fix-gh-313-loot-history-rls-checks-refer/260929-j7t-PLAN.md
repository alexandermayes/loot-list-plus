Planner discretion (documented choices):
- PD-01 (approach, D-02): a trigger, not policy changes. (1) A policy WITH CHECK sees only the new row. It cannot compare NEW with OLD, so it would re-validate every reference on every UPDATE. A notes edit on a legacy mislinked row, or on an award to a raider who has since left the guild (is_active false, a normal state), would then fail. (2) Triggers fire for every role, including service_role, which bypasses RLS. So the same rule also catches a future bug in a service-role route (#277, #294 and #296 were all such bugs), plus migrations and scripts. (3) There is one definition instead of two copies (an INSERT and an UPDATE policy) that must stay in sync. The existing policies stay exactly as they are (no DROP or CREATE POLICY): they keep gating who may write, and the trigger gates what the row may point at. The drop-and-recreate policy pattern in 20260804000001_standardize_guild_permission_helpers.sql is therefore not used.
- PD-02: The function is SECURITY DEFINER with SET search_path TO 'public', 'pg_temp' and schema-qualified table names, like is_guild_officer and reject_submissions_on_cgm_loss. Its lookups therefore never depend on the caller's RLS view of raid_events, character_guild_memberships or the catalog tables. EXECUTE is revoked from PUBLIC, anon and authenticated (the 20260722000001 lockdown pattern). The planner's PGlite probe confirmed that the trigger still fires for authenticated and service_role after the REVOKE, and that a direct call fails with 42501. The body is read-only.
- PD-03 (D-07): INSERT checks every reference. UPDATE checks a reference group only when it changed: the raid event when raid_event_id changes, the raider when character_id changes, and the item group when loot_item_id, raid_tier_id or expansion_id changes. If guild_id changes, all three groups are checked. The trigger is declared UPDATE OF those six columns, so a notes-only or awarded_date-only UPDATE does not call the function at all. The NEW vs OLD comparison inside still covers a PATCH that re-sends unchanged values. Justification: the rule's job is to stop a write from creating a new foreign link. A column the write did not change creates no new link. The rule also keeps raid event deletion working, because its ON DELETE SET NULL action is an UPDATE of raid_event_id on rows that may point at departed raiders. The trigger does not repair legacy rows. Production had zero item mislinks as of 2026-09-28 (#289's count query).
- PD-04: If NEW.guild_id is NULL, the trigger returns NEW at once. If loot_item_id is NULL, it skips the item group. If raid_tier_id is NULL, it skips the tier comparison. In each case the column's NOT NULL constraint then rejects the row with its usual 23502, so the #294 schema contract's missing-column errors are unchanged.
- PD-05: A NULL expansion_id is allowed: the column is nullable, legacy rows have NULLs, and NULL points at no other guild. A non-NULL expansion_id must equal the item's tier's expansion_id (see OD-2).
- PD-06: raid_tier_id must equal the item's own loot_items.raid_tier_id. It is not enough for the tier to be any tier of the guild. Every server builder already writes item.raid_tier_id (lib/loot/loot-history-rows.ts, since #294).
- PD-07: Violations raise SQLSTATE 23514 (check_violation), which PostgREST returns as 400. Each MESSAGE is a fixed string with no ids and no % format marker. The caller-supplied id and the row's own guild_id go in DETAIL only. A nonexistent id and another guild's id get the same message. Because this is a BEFORE trigger, it runs before the raid_event_id FK check, so there is no existence oracle, and no message ever names the guild that owns a foreign row. No message, DETAIL format string or COMMENT text contains a semicolon or two consecutive hyphens, so the shape test's comment stripper and splitter stay safe.
- PD-08: Names. Migration supabase/migrations/20260929180000_enforce_loot_history_guild_refs.sql. Function and trigger are both named enforce_loot_history_guild_refs. The test is app/services/__tests__/loot-history-guild-refs-migration.test.ts, next to the four existing migration shape tests. There is no BEGIN/COMMIT (no recent migration uses one) and no database.types.ts change (trigger functions are not in the generated types).
- PD-09: The PGlite proof lives only in HARNESS (scratchpad), as in #289, #294 and #300. Its DDL copies the needed baseline statements verbatim, with the deviations listed in Task 1. It runs the real migration file from WT, and its output is summarized in the PR body.
