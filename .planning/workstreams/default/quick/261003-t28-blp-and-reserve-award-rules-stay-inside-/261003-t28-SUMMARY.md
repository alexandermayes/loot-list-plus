# Quick Task 261003-t28: BLP and Reserve Award Rules Stay Inside the Guild Summary

**Drops six unused officer write policies on blp_credits/blp_tracking and adds a BEFORE INSERT OR UPDATE trigger (enforce_reserve_award_refs) that keeps a reserve_awards row pointing at a submission and a loot item of its own reserve run, for every caller including service_role, plus a matching up-front check in the awards route.**

## Accomplishments

- blp_credits and blp_tracking are now writable only by the server functions that rebuild BLP (the three recompute functions, increment_blp, increment_blp_bulk, reset_blp, reset_guild_season, delete_guild, and referential actions); the six officer INSERT/UPDATE/DELETE policies on these tables were dropped because no writer ever used them (every writer is SECURITY DEFINER or a referential action, which RLS never governs for the table owner).
- A new SECURITY DEFINER trigger, enforce_reserve_award_refs, keeps a reserve_awards row pointing at a submission of its own reserve run and (per OD-1 resolution A) a loot item in the run's raid tier, for every role including service_role; UPDATE checks only a reference the write changes, so legacy rows and ON DELETE SET NULL stay working.
- The reserve awards route (POST /api/reserve-runs/[id]/awards) now validates the same two references before writing and answers 400 with a clear message instead of letting the database trigger turn a mismatch into a 500 (orchestrator amendment A1).
- One migration-only PR body draft and one app PR body draft written to the scratchpad, ready for the user to open as two PRs.

## Decisions Made

- OD-1 resolved as option A (user, 2026-10-04): the database also requires the awarded item to be in the run's raid tier, not just the submission to belong to the run. The run page already offers only the items of the run's raid tier, so no app award is affected; the item rule follows the run's raid tier rather than the run's guild, since GET /api/reserve-runs/raid-tiers lists tiers from any guild's data and a guild's run often uses a raid tier (and items) seeded by another guild.
- COPY sign-off (user, 2026-10-04): both trigger error messages approved as drafted (C-1 "reserve_awards.submission_id is not a submission of this reserve run", C-2 "reserve_awards.loot_item_id is not in the raid tier of this reserve run"). Neither is shown in the app: the route answers its own generic/mismatch text, and the route page only ever sends matching pairs.
- Orchestrator amendment A1 (user-approved scope addition): rather than leaving a mismatch to surface as an opaque 500 from the new trigger, the awards route now checks the same two references up front and answers 400 with "This award doesn't match this reserve run. Refresh the page, then try again." Shipped as its own app commit after the migration commits so it can ship as a separate PR, mergeable in either order relative to the migration PR.

## Context Findings (recorded per D-06)

1. **Rules today** (verified in the worktree at 55f2c688, no migration after the baseline changes any policy of these four tables): blp_credits and blp_tracking had SELECT for active guild members (blp_tracking also for the guild creator) and INSERT/UPDATE/DELETE for `is_guild_officer(guild_id)`; reserve_awards had SELECT for active members of the run's guild, INSERT and DELETE for an officer of the run's guild, no UPDATE policy; reserve_submissions had only SELECT; reserve_runs INSERT needed only a signed-in caller and UPDATE/DELETE the creator or an officer.

2. **BLP writers and readers** (git grep over every tracked file): every writer of blp_credits/blp_tracking is a SECURITY DEFINER function (recompute_blp_for_item, recompute_blp_for_event, recompute_blp_for_guild, increment_blp, increment_blp_bulk, reset_blp, reset_guild_season, delete_guild) or a referential action (character/guild/loot item/raid event deletes, expansion delete SET NULL). No app path ever wrote these tables with a user session. Readers: the dashboard (`DashboardContent.tsx`), GET /api/blp (service role, after an active-membership check), and the addon exports (already tracked as broken against a nonexistent table name in a separate pending todo, unrelated to this task).

3. **reserve_awards and reserve_submissions writers and readers**: the only INSERT path is `POST /api/reserve-runs/[id]/awards` (service role, after `verifyReserveRunAccess`), which sends `loot_item_id`, `character_name`, and `submission_id` or NULL from the request body; the page itself sends only a submission and item of the same run, but the route did not check this server-side before this task's A1 amendment. `reserve_submissions` is written only by the join route (after an active-membership check) and by the officer edit/delete routes (which never change `character_id` or `reserve_run_id`), all through the service role.

4. **Probe facts** (synthetic seed, four reserve runs on guild A/tier A, guild B/tier B, guild A/tier B, and no guild/tier A): before this migration, an officer session could insert/update/delete both BLP tables including rows naming another guild's character and a hand-set `times_passed`; a non-officer got the ordinary RLS error. An officer could award an item naming another run's submission or an item of another tier; the policy could not catch this because it only checks officer status of the run's guild. `is_guild_officer(NULL)` is false, so a guild-less run's award path depends entirely on the creator or raid-leader-token actor, matching `reserve_runs_insert`'s "signed-in caller" rule.

5. **Tests**: every migration shape test in this codebase is anchored to a fixed timestamp (not a live directory scan, per #309) and uses the same `stripComments`/`splitStatements`/`rollbackStatements` helper shapes first established for `enforce_loot_history_guild_refs` and reused by quick task 261003-m45; the function-execute-grants ratchet test (`function-execute-grants-migration.test.ts`) requires every new public function in a later migration to REVOKE from PUBLIC, which this migration's statement 10 satisfies.

**1. [Rule 1 - Bug] Reworked the award test helper to avoid INSERT ... RETURNING for session-role writes**
- **Found during:** Task 1 (writing the PGlite scenario)
- **Issue:** The scenario's first draft of the `award()` test helper used `INSERT ... RETURNING id` so it could clean up by id. This surfaced a real Postgres RLS behavior (not a bug in the migration): `RETURNING` also applies the table's SELECT policy to the new row, and GM_A (an officer only via `guilds.created_by`, with no character) fails `reserve_awards_select` (which requires an active membership via a character) even though `reserve_awards_insert`'s own WITH CHECK passes. This produced a false "masked" result for GM_A's award attempts (T28-RA-3), which does not reflect how the app actually writes (always via the service role, which bypasses RLS).
