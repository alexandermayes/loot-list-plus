Fix two officer-side loot list actions on the loot lists page (app/(app)/loot-submissions):

1. GH #352: Delete pending and Delete all remove only the officer's own lists. The bulk path of the delete route runs with the officer's own session after the permission check, and the loot_submissions delete policy lets only a list's owner delete it, so every other raider's list is skipped without an error while the toast reports the full count.
2. GH #353: Undo after approving or rejecting a list is refused. The page sends status pending to the review route, which only reviews pending lists, and the page then tells the officer to fix it manually, which no screen allows.

Purpose: officers need to clear lists for their guild and to recover from a misclicked review. Both flows are broken today; the fix keeps each change inside the officer's guild, keeps the snapshot and review trail that revert and the review diff rely on consistent, and keeps raiders from getting a Discord message about a review that was undone.

- D-02 (bulk delete server): in app/api/loot-submissions/delete/route.ts (the handler is DELETE, not POST as the issue says) the bulk path keeps the existing guild_id, target and permission checks and their texts, then reads submission_ids from the body. Valid means an array of at most BULK_DELETE_MAX_IDS entries, each a string matching the UUID pattern used in lib/loot/guild-award-refs.ts (copy the regex as a local constant; do not export it from there); anything else returns 400 { error: COPY C-1 } before any database call (validation order: guild_id, target, submission_ids, then verifyPermission, so a malformed request never reaches the database). De-duplicate. An empty list returns 200 { success: true, count: 0, requested: 0, message } with no delete. Otherwise, for each chunk of BULK_DELETE_CHUNK_SIZE ids, serviceSupabase.from('loot_submissions').delete().eq('guild_id', guild_id).in('id', chunk).in('status', [...BULK_DELETE_STATUSES[target]]).select('id, character_id, status'), collecting the returned rows (chunks keep the PostgREST query string short; one id list in a single request could exceed URL limits). The separate pre-delete fetch is removed: the rows the delete returns are exactly what was deleted. The user-session client (createClient from @/utils/supabase/server) is no longer created anywhere in this route; drop its import. Items and snapshots go with the list (ON DELETE CASCADE; the item rules trigger does not check the service role).

## Investigation findings (verified in WT at 8019a27d)

1. #352 root cause. The bulk path fetches the lists to report (112-121), deletes (125-134) and writes the audit entry (143-157) with the officer's own session. loot_submissions has exactly one DELETE policy, loot_submissions_delete, which requires the list's character to belong to auth.uid(). So the delete removes only the officer's own lists, raises no error, and the response count (taken from the earlier fetch, which officers can read for the whole guild) reports every list as deleted. The bulk path is also scoped by guild alone: every expansion and phase, and for Delete all also drafts, while the page shows only the selected expansion and phase tab and never drafts. The page does not refresh the sidebar badge after a delete and does not reload the list after an error.
2. Deleting with the service role is clean: loot_submission_items and loot_submission_snapshots cascade, and the item rules trigger returns early for any role other than anon and authenticated. No other table references loot_submissions. The only server cache that holds loot list data is the pending-count tag, which both routes revalidate.
3. #353 root cause. The review route accepts status pending in its validation but returns 400 "Can only review pending submissions" for any list that is not pending, so every undo fails. The page ignores the server text and shows "Couldn't undo. Try manually from the submission list.", but no screen can move an approved list back: the review route needs a pending list and revert needs a pending resubmission.
4. Snapshots. Approval deletes every snapshot of the list and inserts version 0 (errors ignored). Readers: the page's review modal (latest by version, maybeSingle), revert (latest by version, single) and the two research queries (EXISTS, and latest by snapshot_at before an award). All of them work with more than one row per list. Because approval deletes the previous snapshot, an undone re-approval cannot restore the state that revert and the diff need unless approval keeps it (D-06).
5. Review trail. A list waiting for review has review_notes, reviewed_at, reviewed_by and change_rejected_at NULL and its reminder fields reset (submit and auto-save), so an undo can restore that state exactly. The review route never sets reviewed_by. The membership-loss trigger can auto-reject an approved list (review_notes and reviewed_at set); an undo of that is refused by R1 and the pre-check.
6. Notifications. The page sends the Discord DM right after the review succeeds (fire and forget). There is no "review undone" DM type. Guild funnel milestones (evaluateGuildFunnel on approval) are written once and are not reversed by an undo. app/(app)/master-loot/_client.tsx calls the review route only with approved or rejected, sends no DM and has no undo, so it is unaffected.
7. Tests. The delete route has no tests; the review route has a recording fake client; LootSubmissionsContent has no component tests (the helpers in D-01 and D-08 carry the tests). eslint on the three existing files exits 0 with 4 warnings, all in LootSubmissionsContent.tsx (lines 36, 351, 460, 901).
