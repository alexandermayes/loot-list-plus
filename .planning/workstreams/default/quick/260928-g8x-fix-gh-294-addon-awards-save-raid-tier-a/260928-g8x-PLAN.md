<objective>
Fix GH #294. Addon and companion awards fail with 500 because POST /api/addon/loot-award and POST /api/addon/import-string insert loot_history rows without raid_tier_id (NOT NULL, no default, no trigger). Separately, POST /api/loot-history/bulk writes the client's loot_item_id and raid_tier_id unchecked, and import-string writes a supplied lootItemId unchecked, which is how awards could point at another guild's rows (#289).

Purpose: officers can record awards from the addon and companion again, and no award write path can link a guild's history to another guild's catalog. This must merge before the #289 repair migration so the repair is not undone by new cross-guild writes.

Output: guild-scoped lookup extended (expansion_id, batch id check), a typed pure row-builder module, three fixed routes, unit tests, a scratchpad PGlite contract run, and one draft PR.

Task decisions from the user's request (locked; referenced by ID below):
- D-01: Addon routes set raid_tier_id and expansion_id from the #292 guild-scoped lookup (lib/loot/guild-scoped-lookup.ts), extended to return expansion_id. Compare with the columns the bulk route sets for consistency.
- D-02: Bulk and import-string resolve each client-supplied loot_item_id within the calling guild on the server through a new batch helper in the #292 module; raid_tier_id and expansion_id come from that resolution, not the request.
- D-03: Ids the guild does not own are rejected with a clear 400 listing the bad ids, never silently dropped.
- D-04: Existing behaviour for valid requests stays: BLP, raid_event_id, upserts and dedupe. (The bulk route has no upsert today; its dedupe path is the per-row insert mapping Postgres 23505 to 'duplicate'. The executor confirms with grep and notes it in the SUMMARY.)
- D-05: Every loot_history insert payload in these three routes is typed against Database['public']['Tables']['loot_history']['Insert'] so a missing required column fails tsc.
- D-06: Tests: route unit tests (cross-guild rejection, payload carries raid_tier_id and expansion_id) plus a PGlite schema-contract check, PGlite installed only in a scratchpad folder, run as a scripted step whose output goes into the SUMMARY and PR body, fed by a pure row-builder per route.
- D-07: Delivery constraints from the orchestrator (worktree, branch, draft PR, merge order before #289, no merge, no --admin, no push to main, no SQL on real databases, commit trailer).

Planner discretion (documented choices):
- PD-01: Addon rows do not gain raid_event_id. Neither addon route resolves a raid event today; linking one would need date-plus-team routing and would change BLP credit and the unique-award dedupe index for those rows, which is new behaviour beyond #294. Listed under "Not in this PR".
- PD-02: resolveGuildLootItem returns a new ResolvedGuildLootItem (GuildLootItemRow plus expansion_id). GuildLootItemRow and findGuildLootItemsByWowheadIds stay unchanged so the raid-tracking caller and its tests are untouched.
- PD-03: The batch helper is resolveGuildLootItemIds. It dedupes ids, pre-rejects ids that are not canonical UUIDs (so hostile input gets a 400 instead of a Postgres 22P02 turned 500), and queries loot_items in chunks of 100 ids to keep PostgREST URLs short.

The helper cannot tell "another guild's id" from "no such id" without an unscoped existence query, and that query would itself reveal other guilds' ids, so the error text says the items are not in this guild. Proposed text (user-facing, no em dashes, flagged for sign-off at PR review): "Loot items not found in this guild: " followed by the comma-separated ids.
- PD-05: Row builders live in lib/loot/loot-history-rows.ts because Next.js App Router route files may only export route handlers. Builders take today's date as an argument so they stay pure and deterministic. The module has zero runtime imports (type-only imports only) so the PGlite script can import it directly through tsx without the @/ alias.
- PD-06: The bulk builder does not set source, so rows keep the DB default 'web' exactly as today.
- PD-07: import-string rejects the whole import with 400 when any supplied lootItemId is not in the guild (per D-03), instead of falling back to the award's wowheadId.
