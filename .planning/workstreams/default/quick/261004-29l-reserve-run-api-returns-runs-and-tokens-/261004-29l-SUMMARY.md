## User decisions applied (resolved 2026-10-04, per the plan's OD table)

- **OD-1 A:** any active member of a guild run's guild may view it read-only, including officers without Manage reserves.
- **OD-2 A:** a run with no guild is opened only by its creator and leader-link holders; no page links a non-manager to such a run.
- **OD-3 A:** while a run is open and hidden until lock, a non-manager sees who signed up (name, class, spec) and how many items each reserved, not which items; managers see everything.
- **OD-4 A:** run history (the Audit log card) is visible to managers only.
- **COPY sign-off:** no new user-facing text; every refusal reuses an existing string (`Not a guild member`, `Forbidden`, `Unauthorized`, `Internal server error`) in a new place, listed in the plan.
- **261004-0us OD-3 (recorded, not re-opened here):** a guild run's creator manages it only while an active member of that guild; the leader link and officers with Manage reserves are unaffected; a run with no guild keeps the plain creator rule. Implemented via `creatorMayManage` in `utils/reserve-access.ts`.

## Access rules (final)

- **Manager** of a run: the raid-leader-token holder; the run's creator, for a run with no guild always, for a guild run only while an active member of that guild (`creatorMayManage`); for a guild run, an officer holding Manage reserves.
- **Viewer** of a guild run (not a manager): any active member of that guild. A run with no guild has no viewers who are not managers.
- Every new access decision fails closed: a membership-lookup database error is thrown by `hasActiveGuildMembership` and every calling route answers `500 { error: 'Internal server error' }` with a constant first argument to `console.error`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `app/api/reserve-runs/route.ts`'s list query lost its narrow embed typing once the select string carried a variable**
- **Found during:** Task 2 (writing `RUN_LIST_COLUMNS` into the list route's select template literal)
- **Issue:** Supabase's generated types narrow an embed's cardinality (to-one vs to-many) by parsing a literal select string at compile time. Once the string interpolated `${RUN_LIST_COLUMNS}`, TypeScript could no longer narrow `raid_tiers(name)` to a single object and inferred an array instead, breaking the existing flattening code's type.
- **Fix:** Widened the map callback's local type to accept `raid_tiers` as either shape and added a one-line normalize (`Array.isArray(...) ? [0] : value`) before reading `.name`. No runtime behavior change; the embed is still a to-one relation at the database level.
- **Files modified:** `app/api/reserve-runs/route.ts`
- **Verification:** `npx tsc --noEmit` clean; list route tests pass, including the column-list assertion.
- **Committed in:** `cbc7ee51` (Task 2 commit)
