<objective>
Fix GH #289. Before PR #292 (merged 2026-09-28 as d06516a1), POST /api/addon/loot-award (also used by the companion app) and POST /api/addon/import-string resolved wowhead_id to loot_items with an unscoped service-role lookup that took the first match. Every guild has its own catalog copy (loot_items -> raid_tiers.expansion_id -> expansions.guild_id), so a loot_history row can point at ANOTHER guild's loot_items row. The raid-tracking import posts client-chosen ids to /api/loot-history/bulk, which never checks ownership. loot_history.loot_item_id is ON DELETE CASCADE, so those awards are silently deleted if the other guild removes the item, its tier, its expansion or the guild itself.

This plan delivers:
- GH-289-R1: one idempotent repair statement in a new migration. It re-points mis-linked rows to the row guild's own item with the same wowhead_id, in the user's match order: (a) same tier name, (b) same expansion name, (c) the active expansion. The first level with exactly one candidate wins. Otherwise the row is left alone. Only loot_item_id is updated.
- GH-289-R2: commented, read-only verification queries in the same file: (1) mis-linked count by source, before and after; (2) unmatched rows with a reason; (3) confirmation that nothing else changed; plus an optional Q4 undo map (OD-03).
- GH-289-R3: the audit of every current loot_history.loot_item_id write path, done at plan time (audit_findings below). The executor re-confirms it against the worktree and puts it in the PR body.
- GH-289-R4: a vitest file that locks the SQL shape, following app/services/__tests__/aq20-phase-backfill-migration.test.ts and classic-loot-backfill-migration.test.ts.

Out of scope, and deliberately not done: any blocking trigger or constraint (described as an optional follow-up in the PR body only), any route or code change, and any repair of loot_history.raid_tier_id or expansion_id (OD-01, a user decision).

Purpose: awards saved against another guild's catalog rows become the guild's own again, so they stop disappearing when that guild edits its catalog, and they match the guild's item-keyed views.
Output: one migration, one test file, a pushed branch fix/289-relink-awards, and one DRAFT PR.
</objective>

## OD-01 (OPEN, user decision): loot_history.raid_tier_id and expansion_id may also point at the other guild

Facts, verified in origin/main code at plan time:
- The only write paths that could have produced cross-guild rows and actually succeed are POST /api/loot-history/bulk and POST /api/loot-submissions/remove-item (see audit row 1 for why the addon inserts likely never succeeded). Both take raid_tier_id from the same item they link. The bulk route also derives expansion_id from the first item's raid_tier_id. So a mis-linked row almost certainly carries a foreign raid_tier_id too, and a foreign expansion_id if it came from bulk.
- loot_history.raid_tier_id is ON DELETE CASCADE to raid_tiers. After this migration fixes loot_item_id, such a row is still silently deleted if the other guild deletes that tier, its expansion or the guild. The #289 deletion risk is only half-closed for those rows.
- expansion_id is already treated as unreliable by analytics (scripts/analytics/queries/wow-classic-loot-systems-2026/05-expansion-distribution.sql).

Planned: honor the instruction "Update ONLY loot_item_id". Q1 reports raid_tier_also_foreign and expansion_also_foreign per source, so the size is known before merging.
Options: (a) as planned, with a follow-up migration that re-points raid_tier_id to the new item's tier and expansion_id to that tier's expansion; (b) widen this migration to do that too. That means lifting the "only loot_item_id" rule and re-planning the SET lock, Q3 and the mutants. Recommendation: if Q1 "before" shows raid_tier_also_foreign above 0, do (b) or ship (a)'s follow-up in the same deploy window.

## OD-02 (planner addition, needed for a safe deploy): skip rows that would duplicate an award

loot_history has a partial unique index idx_loot_history_unique_award on (guild_id, loot_item_id, character_id, raid_event_id) WHERE both raid_event_id and character_id are NOT NULL. A plausible case: an officer saw an award "missing" and awarded it again with the guild's own item. Re-pointing the mis-linked copy would then violate the index. A unique violation aborts the whole statement. scripts/deploy-migrations.sh would exit without recording the version, and every later migration would be blocked. The plan therefore leaves such rows untouched, including two mis-linked rows that would resolve to the same key, and Q2 reports them as 'would duplicate an existing award'. Deleting the duplicate is not an option under "update only loot_item_id"; it stays a manual cleanup the user can do from Q2.

## OD-03 (planner addition, optional): Q4 undo map

Nothing in the database records the old loot_item_id after the repair. Q4 lists history id, old item id and new item id for exactly the rows the statement will change. Run it before merging and save the output; it is the only undo map. The query is read-only and can be dropped if the user does not want it.

THE EXECUTABLE STATEMENT (the contract the test locks). Line breaks and indentation may differ. Tokens, aliases, CTE names, column aliases, predicate text and CTE order may NOT. No inline comments inside the statement; every explanation goes in the header.

```sql
WITH linked AS (
  SELECT h.id AS history_id,
         h.guild_id,
         h.character_id,
         h.raid_event_id,
         h.source,
         cur.wowhead_id,
         cur_rt.name AS tier_name,
         cur_e.name AS expansion_name
  FROM public.loot_history h
  JOIN public.loot_items cur ON cur.id = h.loot_item_id
  LEFT JOIN public.raid_tiers cur_rt ON cur_rt.id = cur.raid_tier_id
  LEFT JOIN public.expansions cur_e ON cur_e.id = cur_rt.expansion_id
  WHERE cur_e.guild_id IS DISTINCT FROM h.guild_id
),
candidates AS (
  SELECT l.history_id,
         li.id AS item_id,
         (rt.name = l.tier_name) AS tier_match,
         (e.name = l.expansion_name) AS expansion_match,
         (e.id = g.active_expansion_id) AS active_match
  FROM linked l
  JOIN public.guilds g ON g.id = l.guild_id
  JOIN public.expansions e ON e.guild_id = l.guild_id
  JOIN public.raid_tiers rt ON rt.expansion_id = e.id
  JOIN public.loot_items li ON li.raid_tier_id = rt.id AND li.wowhead_id = l.wowhead_id
),
level_counts AS (
  SELECT history_id,
         count(*) AS candidate_n,
         count(*) FILTER (WHERE tier_match) AS tier_n,
         count(*) FILTER (WHERE expansion_match) AS expansion_n,
         count(*) FILTER (WHERE active_match) AS active_n
  FROM candidates
  GROUP BY history_id
),
chosen AS (
  SELECT c.history_id, c.item_id
  FROM candidates c
  JOIN level_counts n ON n.history_id = c.history_id
  WHERE (n.tier_n = 1 AND c.tier_match)
     OR (n.tier_n <> 1 AND n.expansion_n = 1 AND c.expansion_match)
     OR (n.tier_n <> 1 AND n.expansion_n <> 1 AND n.active_n = 1 AND c.active_match)
),
targets AS (
  SELECT ch.history_id, ch.item_id, l.guild_id, l.character_id, l.raid_event_id,
         count(*) OVER (PARTITION BY l.guild_id, ch.item_id, l.character_id, l.raid_event_id) AS same_target_n
  FROM chosen ch
  JOIN linked l ON l.history_id = ch.history_id
),
safe AS (
  SELECT t.history_id, t.item_id
  FROM targets t
  WHERE t.character_id IS NULL
     OR t.raid_event_id IS NULL
     OR (t.same_target_n = 1
         AND NOT EXISTS (
           SELECT 1 FROM public.loot_history k
           WHERE k.guild_id = t.guild_id
             AND k.loot_item_id = t.item_id
             AND k.character_id = t.character_id
             AND k.raid_event_id = t.raid_event_id))
)
UPDATE public.loot_history lh
SET loot_item_id = s.item_id
FROM safe s
WHERE lh.id = s.history_id;
```

Why each piece (for the header and the SUMMARY; do not put this inside the statement):
- linked: LEFT JOINs, so an item whose tier or expansion chain is broken also counts as mis-linked, exactly per IS DISTINCT FROM. h.source is carried only so Q2 can report it.
- candidates: only the row's OWN guild's items (e.guild_id = l.guild_id) with the same wowhead_id. A linked item with a NULL wowhead_id matches nothing and falls to 'no item in the guild'. A NULL tier_name, expansion_name or active_expansion_id makes that level's match NULL, and FILTER and WHERE treat NULL as false.
- chosen: the three branches are mutually exclusive, so each history row yields at most one item. Level (b) is tried only when (a) did not yield exactly one; (c) only when neither did.
- targets and safe: OD-02. The escape on NULL character_id or raid_event_id mirrors the unique index's WHERE clause.
- Idempotency: a repaired row links to its own guild's item, so linked no longer selects it. Every unrepaired row depends only on catalog rows and on its own columns, which the statement does not change, so it gets the same outcome on every run. A second run changes zero rows.
