<objective>
Fix GH #314. The master sheet lists raiders who have left the guild, or were removed, as award candidates when they still have an approved loot list. The award path rejects them ("Some raiders aren't active members of this guild. Check the roster, then try again."). This plan filters the candidate set at its single source, POST /api/master-sheet/visibility. It uses the same active-member definition as the award check, so the sheet, the award modal and the Gargul export only show raiders who can actually be awarded.

Purpose: an officer handing out loot mid-raid should never pick a candidate the server will refuse. Departed raiders also push active raiders down the Loot Score order today.

Output: one small pure helper, the route filter, tests, corrected comments, and one draft PR. No migration.

3. How departed raiders keep approved lists (investigation 3, public-safe version):
- trg_reject_submissions_on_cgm_loss (baseline_schema.sql function ~856-907, trigger ~3006; first added 20260514000003, commit 783b18ff) fires AFTER UPDATE OR DELETE on character_guild_memberships. On an active-to-inactive UPDATE (COALESCE-guarded, so NULL counts as inactive) or on a DELETE of an active row, it flips that (character, guild)'s pending and approved lists to rejected.
- Covered, no gap: CGM is per character, UNIQUE (character_id, guild_id) (baseline ~2514), so alts are handled one by one. Leave (guilds/leave/route.ts ~75), kick (guild-members/route.ts ~422), removing a character from a guild (characters/[id]/guilds/route.ts ~309) and account deletion (user/delete-account/route.ts ~142, a delete) all fire it. No code path changes a CGM row's guild_id or character_id. Rejoin (guild-invites/[code]/route.ts ~233, discord-guilds/join/route.ts ~216, battlenet import upsert ~323) reactivates the CGM, but the lists stay rejected, so the raider resubmits and an officer re-approves. Rejoin does not bring back a stale list.
- Pre-trigger data: migration 20260514000001 (commit 9ceaa67b), shipped the same day as the trigger, backfilled by REACTIVATING the CGM of every character with a pending or approved list (13 rows on production). So on 2026-05-14 every approved list had an active CGM. No pre-trigger leftovers are expected.
- The gap: the trigger only watches character_guild_memberships. Nothing checks membership when a loot_submissions row changes status (there is no trigger on loot_submissions). So once the CGM is already inactive, a list can become approved again. The manual Save/Submit path saveSubmission (app/contexts/LootListContext.tsx ~879-930) has no active-membership check, unlike auto-save (~767-770, "Your character needs to rejoin this guild."). POST /api/loot-submissions/submit checks only that the caller owns the character (submit/route.ts ~52-61) and promotes the list to pending from any status (~143-155). An officer then approves it via POST /api/loot-submissions/review, which checks only the officer's permission and pending status (review/route.ts ~54-61). POST /api/loot-submissions/revert sets approved (~138) with no membership check either. Example: a raider is kicked while their loot list tab is open, clicks Submit, and an officer approves it from the review queue. The result is an approved list with an inactive CGM, shown on the master sheet and rejected at award time. This is FU-1.
