# Quick Task 260929-n27: Fix GH #314 (master sheet showed departed raiders as award candidates) Summary

**Filtered master sheet candidates to active guild members at their single source route, reusing the award check's own membership definition so the sheet and the award path can never disagree.**

## Performance

- **Duration:** ~45 min
- **Tasks:** 3
- **Files modified:** 5

## Accomplishments

- `POST /api/master-sheet/visibility` now drops any candidate whose character has no active `character_guild_memberships` row in the guild, using `findInvalidCharacterIds` (the same function the bulk award routes and the `loot_history` guild-reference trigger already use).
- New pure helper `domain/loot/master-sheet-candidates.ts` (`splitCandidatesByMembership`) does the actual filtering; it also returns `departedCharacterIds` so a future greyed-out display needs no change to the helper, only to how the route uses its output.
- A contract test proves the sheet's kept-character set exactly equals the complement of what `findInvalidCharacterIds` reports as invalid, for the same fixture data, so the sheet and the award check cannot drift apart again.
- A membership-lookup error returns a 500 with the route's existing generic error body; it never falls back to showing an unfiltered or empty list.
- Every master sheet consumer (Rankings view, award modal, Gargul/CSV export) inherits the fix automatically, since none of them do their own filtering; three stale comments in `MasterSheetContent.tsx` describing the old bug were corrected (comment-only, verified by a mechanical diff check).
- Investigated and confirmed FU-2 directly: `app/api/bot/priority/route.ts` selects `loot_submissions.items`, a column that does not exist on that table's schema, so the Discord bot's priority lookup likely already returns no raiders for any query, independent of this fix. Not touched in this PR.
- One draft PR (#324) opened to `main`, carrying the root cause, the surfaces audit table, OD-01/OD-02 as open decisions, and the three proposed follow-up issues (FU-1 through FU-3) for review.

## Decisions Made

- **OD-01 (hide vs. grey out departed raiders):** implemented as hide, per the plan's recommendation. Every award path already rejects an inactive member, so a greyed row would be an un-awardable candidate and noise mid-raid; hiding also restores the true Loot Score order and needs no new copy. The helper's `departedCharacterIds` output is preserved specifically so a later switch to greyed-out is a small, contained change. The user confirmed hide after review.
- **OD-02 (fix the write-side gap in this PR?):** decided no by the user after review. Only the read-side filter ships here. The write-side issue (a resubmitted list can become approved again after the raider's membership goes inactive, since neither the submit, review, nor revert routes check membership) is FU-1, handled in a separate change.
- **FU-2 investigated per the plan's Task 3 Step A**, confirming (not fixing) that the Discord bot's priority route selects a nonexistent `items` column on `loot_submissions`, so it is likely already non-functional independent of GH #314. Reported only, no code change.
- **FU-3** (Summary view, export-string's legacy zero-active-CGM fallback, phase gate counting a departed alt) reported only, no code change, per the plan.
