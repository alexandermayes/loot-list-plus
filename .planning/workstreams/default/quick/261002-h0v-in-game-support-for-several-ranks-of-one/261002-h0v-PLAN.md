## Locked design decisions (planner design; referenced by ID in the tasks)
- D-01: addonAwardKeys({ awardedAt, wowheadId, characterName, awardId }) returns { key, alternateKeys }. Validity rules for the name and wowheadId are unchanged, and either one invalid gives key null.
  - When awardId is a string matching ^[A-Za-z0-9][A-Za-z0-9:._-]{7,63}$ (8 to 64 characters): key = 'addon2:' + awardId + ':' + wowheadId + ':' + trimmed lowercased name, provided it is at most 200 characters. alternateKeys = [the legacy key] when awardedAt is valid, otherwise [].
  - Otherwise, key = the legacy key 'addon:' + awardedAt + ':' + wowheadId + ':' + name (tv5 D-03, unchanged) and alternateKeys = [].
  - addonAwardKey(input) stays exported and returns addonAwardKeys(input).key, so existing callers and tests keep working.
  - The wowheadId and name are part of the addon2 key, so a reused or tampered awardId can never suppress an award of a different item or raider.
- D-02: insertAddonAward(supabase, row, options?) takes options.alternateKeys.
  - With a non-empty list, keyed step 1 looks up .in('source_award_key', [key, ...alternateKeys]) instead of .eq. Steps 2 and 3 are unchanged and stamp or insert the primary key.
  - With no alternates, every existing query is byte-for-byte unchanged.
  - The alternate covers an out-of-order rollout: an award first stored under its legacy key, by a server or companion that ignored awardId, is not doubled when its awardId arrives later.
  - Accepted cost: two awards of one item to one raider in the same second, the first stored through a legacy-only path, are recorded once (T-h0v-03).
- D-03: POST /api/addon/loot-award reads an optional award_id. POST /api/addon/import-string reads an optional awards[].awardId. Both pass it to addonAwardKeys and pass the alternates to insertAddonAward. A missing or malformed value is never a reason to reject a request; it falls back to today's key.
- D-04 (FU-3 of #331/#293): both export routes select loot_submission_items (loot_item_id, rank, slot, removed_at, loot_items (wowhead_id)) and drop rows with removed_at set.
- D-05: each raider's entries go out in rank ascending order, with slot descending on a tie, so the best rank is last. The current addon (Sync:ProcessImport) and the current companion keep the last entry per item, so they now keep the best rank. withFactionVariants runs after ordering, so mirrors sit right after their source rows. The per-character "last approved submission wins" behaviour is preserved (N-1 is not fixed here).
- D-06 (OD-1): both export routes call fetchReceivedCounts(supabase, guildId).
  - The query reads loot_history with select 'character_id, loot_item:loot_items(wowhead_id)', eq guild_id, ordered by id, in ranges of 1000, checking the error on every page. It counts `${character_id}-${wowhead_id}` and skips null character_id or null wowhead_id.
  - buildMemberRankedItems then drops received entries with pickReceivedEntries, best rank first, on catalog ids before faction mirroring.
  - On a read error the function logs with a constant first argument and returns null, and the export goes out unskipped.
- D-07: toPendingAwardRequests(rawPending) maps each pending award to { wowhead_id, character_name, boss_name, awarded_date, awarded_at, award_id }.
  - awarded_date is the awardedAt date part, exactly as today.
  - awarded_at is the raw awardedAt when it is a string.
  - award_id is the raw awardId when it is a string. Absent values are left undefined, so JSON.stringify drops them.
- D-08: convertMembersToLuaFormat writes items[String(id)] = the highest rank and itemRanks[String(id)] = every rank, highest first, with equal ranks in different slots kept as separate entries. All other member fields are unchanged.
- D-09: convertItemsToLuaFormat marks its keys as numeric. lua-parser.ts records the numeric keys of every parsed non-array table under a non-enumerable Symbol LUA_NUMBER_KEYS (helper markLuaNumberKeys). lua-writer.ts toLuaObject writes a marked key whose text is a finite number as [n]. Every other key keeps today's form: a bare identifier or ["k"]. Member items and itemRanks are never marked.
- D-10: syncNow order is: read pending, push attendance (first, #295), push awards, fetch guild data, then one read-modify-write through applyGuildDataToSavedVars(saved, guildDataLua, clearPending). That call replaces profiles.Default.guildData and empties pendingAwards and pendingAttendance only when the pass had pending data. A fetch failure skips the write, so pending stays and is re-sent. clearPendingInSavedVars is removed. PD-05 is unchanged: failed award POSTs are still cleared after a pass (N-5).
- D-11: companion/src/main/addon-format.ts is pure, using relative imports only (its only import is ./lua-parser). Tests live in companion/src/main/__tests__ and run in the root vitest suite (CI "Test" job). companion/tsconfig.json gains "exclude": ["src/**/__tests__/**"], so the CI "Companion" job, which installs only companion dependencies, never type-checks vitest imports.
- D-12 (OD-5): the companion version becomes 1.1.0 via npm version 1.1.0 --no-git-tag-version, in a commit of its own.
- D-13 (OD-4): every commit touches only server files or only companion/ files. The server commits are cherry-picked onto a local branch feat/in-game-item-ranks-server from origin/main for the first PR.
- D-14: FU-B is not executed here. See "Follow-up plan FU-B" below. This executor never clones or touches the addon repo.
