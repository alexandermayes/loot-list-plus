<objective>
Enforce loot list status rules in the database for loot_submissions writes, and make the submit, review and revert routes (and the manual save) check active membership up front with clear messages. This also covers the #314 follow-up FU-1 (resubmitting or approving a list did not check that the raider is still an active member).

Purpose: the loot_submissions write policies decide who may write a row (the character's owner or an officer) but not which status the row may take or whether its character is an active member of the row's guild. The officer review route and the submit route enforce those rules, but they write through the service role, and a user session writing through PostgREST is not held to them. After this change the database enforces who can move a loot list to pending or approved, requires an active membership for a list in either state, and keeps the items and review trail of a pending or approved list unchanged unless an officer or the service role writes them.

Output: one migration plus its shape test, membership pre-checks in three routes (with new route tests) and in saveSubmission, and a scratchpad-only PGlite proof. Local commits only in WT; the orchestrator reviews, pushes and opens the PR.

FROM PUBLIC, anon, authenticated, client detection by current_setting('role', true) IN ('anon', 'authenticated'), messages passed with RAISE USING MESSAGE (never as a format string), header comment with Problem, Fix, Why a trigger, Error contract and Rollback sections. The timestamp 20260930000000 is later than 20260929180000 and unique in WT; the existing migration shape tests compare against fixed constants, not a directory scan, so none of them break.
- D-02 (R1, all callers, including service_role): a row may only enter status 'pending' or 'approved' when public.character_guild_memberships has a row with character_id = NEW.character_id, guild_id = NEW.guild_id and is_active = true. "Enter" means: INSERT with NEW.status in ('pending', 'approved'); or UPDATE where NEW.status is in that set and (NEW.status IS DISTINCT FROM OLD.status, or NEW.guild_id IS DISTINCT FROM OLD.guild_id, or NEW.character_id IS DISTINCT FROM OLD.character_id). NULL character_id or NULL guild_id counts as no membership. Transitions into 'draft' or 'rejected' are never blocked. R1 deliberately ignores phase, expansion_id and raid_tier_id changes, because merge_phase_groups (service role) moves approved lists between phases and some legacy approved rows may belong to raiders who have left.
- D-03 (R2, client callers): only an officer of NEW.guild_id (public.is_guild_officer(NEW.guild_id)) may do any R1-type entry, and only an officer may change guild_id, character_id, expansion_id, phase or raid_tier_id of a row whose NEW.status is 'pending' or 'approved' (so an approval cannot be carried to another phase or expansion). Investigation found no app code that writes loot_submissions status from a user session as an officer (every officer action goes through the service-role review, revert and delete routes); officers are still allowed, because it is harmless and keeps the "Officers can manage submissions" and loot_submissions_update officer branches meaningful. R1 still applies to officers.
- D-04 (R3, client non-officers): reviewed_at, reviewed_by, review_notes and change_rejected_at may only be set to NULL or left unchanged (on INSERT each must be NULL). The only client flow that writes them is auto-save, which sets all four to NULL when an approved or pending list reverts to draft. R3 is skipped when pg_trigger_depth() > 1: the character_guild_memberships UPDATE and DELETE policies let a user session change its own membership rows, and reject_submissions_on_cgm_loss then writes review_notes and reviewed_at inside that same session. Only R3 gets this exemption. submitted_at, resubmission_count, resubmit_reminded_at, resubmit_reminder_count, is_late and version are not covered: saveSubmission re-sends a cached submitted_at, and the reminder fields only throttle DMs to the raider themselves; is_late has no reader in app code.
- D-05 (R4, client non-officers, subject to OD-1): an INSERT (the BEFORE INSERT trigger also fires on the insert phase of every PostgREST upsert, even when the row then conflicts and updates), and any UPDATE that changes guild_id or character_id, requires that public.characters has NEW.character_id with user_id = auth.uid() and that the character has an active membership in NEW.guild_id. This matches the live ownership model (every current policy uses character_id to characters.user_id) and auto-save's own membership pre-check, and it makes the legacy user_id-based INSERT and UPDATE policies unable to create or move a row onto a character the caller does not own.
- D-06 (items rule): a BEFORE INSERT OR UPDATE OR DELETE trigger on public.loot_submission_items. For client callers, look up the parent public.loot_submissions row (NEW.submission_id on INSERT, OLD.submission_id on DELETE, both on UPDATE when they differ); if a parent is found with status 'pending' or 'approved' and the caller is not public.is_guild_officer(parent.guild_id), raise 42501. A parent that is not found (NULL submission_id, or a parent already deleted in a cascade) does not block; the foreign key and RLS decide. Non-client callers (service_role: review, revert, remove-item, account and character deletes) are never checked. This covers save_submission_items, which is SECURITY DEFINER and checks ownership but not status, because the role setting is unchanged inside a SECURITY DEFINER function (the #313 trigger relies on the same behaviour). Order check: auto-save and saveSubmission upsert the parent first (to 'draft', or keeping 'rejected') in one request and call save_submission_items in a second request, so the parent is never pending or approved when their item writes run.
- D-07 (snapshots, subject to OD-2): the migration drops the one INSERT policy on loot_submission_snapshots ("loot_submission_snapshots_insert", character owner). No app code writes snapshots with a user session; review writes them and revert reads them through the service role; the officer diff view only reads them. There is no UPDATE or DELETE policy, so after the drop user sessions cannot write snapshots at all.
- D-08 (error contract): any rule failure for a client caller (anon or authenticated, officer or not) raises MESSAGE 'new row violates row-level security policy for table "loot_submissions"' (or "loot_submission_items"), ERRCODE insufficient_privilege, no DETAIL. For a DELETE on items use MESSAGE 'permission denied for table loot_submission_items' with the same code (there is no new row). Any other caller (service_role, postgres, migrations) can only fail R1 and gets ERRCODE check_violation with the fixed MESSAGE 'loot_submissions: a pending or approved list needs an active guild membership' and a DETAIL built with format() naming the rule, character_id, guild_id and status. The officer lookup runs only on the failure path (evaluate each client rule first; call is_guild_officer only if one fails), as in #313.
- D-09 (transition-only, legacy rows): the loot_submissions trigger is BEFORE INSERT OR UPDATE OF status, guild_id, character_id, expansion_id, phase, raid_tier_id, reviewed_at, reviewed_by, review_notes, change_rejected_at, and every rule compares NEW with OLD (OLD read only inside IF TG_OP = 'UPDATE'), so an UPDATE of other columns, or one that re-sends unchanged values, is never blocked. The migration changes no data and validates no existing row.
- D-10 (FU-1 route UX): submit, review (approve only) and revert (snapshot path only) check active membership with findInvalidCharacterIds (lib/loot/guild-award-refs.ts, same definition as the award routes and #314) before any write. A NULL character_id counts as not a member. submit returns 403 with C-1 (matches the route's existing 403 for "You can only submit your own lists"); review and revert return 400 with C-2 (matches the 400 the award routes return for inactive raiders). If the status UPDATE still returns error code '23514' (membership lost between the check and the write), return the same 403 or 400 response. A lookup error propagates to the route's existing catch and returns 500, the #314 rule. Rejecting (review status 'rejected' and the revert no-snapshot fallback) is never blocked.
- D-11 (FU-1 saveSubmission): saveSubmission runs the same membership query as auto-save (character_guild_memberships select id, is_active, eq character_id, eq guild_id, maybeSingle, user client) before its upsert, for both save and submit. On an error or inactive membership it throws new Error with C-1, so the existing catch shows it and the existing setIsSaving(false) after the try/catch still runs (a bare return inside the try would leave the spinner on). Auto-save behaviour does not change.
