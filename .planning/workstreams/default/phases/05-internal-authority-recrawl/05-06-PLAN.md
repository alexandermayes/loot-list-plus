<objective>
Give the sitemap one honest source for every date it publishes, and delete the three places it currently guesses.

**As a** search engine deciding what to re-crawl, **I want to** read a lastmod that means the day the page's content actually changed, **so that** the freshness signal is information rather than noise.

Purpose: `app/sitemap.ts` calls the zero-argument date constructor three times today. On a cached Next.js metadata route that does not read a request-time API, those do not mean now; they mean whenever Vercel last built, which could be weeks ago or could be five minutes ago for a reason that had nothing to do with the page. LINK-02 asks for accurate lastmod, and accuracy is impossible while three entries are reporting the build cadence. This is also the file the production probe cross-checks, so it has to be readable from Python as well as TypeScript.

Output: `data/content-dates.json` as the source, `lib/content-dates.ts` as the typed reader, `lib/CONTENT-DATES.md` as the rule, and a sitemap that restates nothing.
</objective>

<assumption_delta_decision>
**Noun now primary:** the content date. Before this plan a page's date existed in up to five independently maintained places (the sitemap literal, `openGraph.publishedTime`, the JSON-LD `datePublished` and `dateModified`, the rendered time element, and the `/blog` listing array). This plan makes `data/content-dates.json` the chosen single source for the one consumer that must be right, the sitemap, which is a derived-to-chosen transition on the sitemap's side and a one-to-many-to-one transition on the module's.

**Decision:** `add-alongside`.

**Rationale:** the sitemap is fully promoted and reads nothing but the module, but the per-page date copies stay where they are, cross-checked by a parity test in plan 05-07 rather than removed. CONTEXT.md defers the per-page refactor explicitly, and doing it now would touch nine post files inside the deploy that gates the one-shot recrawl.

**Accepted debt:** a blog post's date lives in the module and in its own `page.tsx`, and only a test keeps them equal. Someone editing a post's date without running the suite can still make them disagree.

**What would force a promote:** a second consumer needing per-page dates, or the parity test being weakened or skipped for any post. Either turns the test from a guard into a formality, at which point the per-page copies have to go.

**Invariant test suggested:** the plan 05-07 parity test is exactly this invariant; it should stay parameterized over all nine posts with no allowance for an exempt slug.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| committed dates source → published sitemap → crawlers | A lastmod is a public assertion about when content changed; a wrong one is a false statement, not a cosmetic defect |
| TypeScript sitemap → Python production probe | Both must read the same literal dates; a duplicated literal set on either side can silently diverge |
| build-time evaluation → production output | A cached metadata route freezes any current-time value at build, so a value that reads as dynamic is static in the only environment that matters |
