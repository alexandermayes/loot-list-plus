## Typography

This phase is a **measure constraint**, not a type-scale change (TYPE-01 through TYPE-04 already shipped the scale in Phases 07/09). No font-size, font-weight, or existing `[&_p]:...`/`[&_h2]:...` arbitrary-variant class inside the shared prose block changes — D-01 is explicit that the prose typography block "stays exactly as it is, verbatim." The table below is reproduced from the existing shipped scale for checker completeness only.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 13px (`text-base`) | 400 (regular) | 1.5 |
| Label | 11–12px (`text-11`/`text-12`) | 500/600 (medium/semibold) | 1.5 |
| Heading | 18–32px (`text-xl`–`text-4xl`) | 600–700 (semibold/bold) | 1.2 |
| Display | 40–80px (display aliases) | 700 (bold) | 1.02 |

**Live finding not in `11-CONTEXT.md` (relevant to the measure calculation, not a contract change):** the four target page types apply no explicit Tailwind font-size *utility* class to their prose paragraphs — `@tailwindcss/typography` is **not installed** (`grep -n "typography" package.json tailwind.config.js` returns nothing), and `app/globals.css` defines no custom `.prose` rule. The `prose prose-invert prose-lg max-w-none` tokens in every target page's className are dead weight — they generate no CSS today and never have. The only typography actually applied comes from the `[&_p]:...`/`[&_h2]:...` arbitrary-variant chain, which sets *color* and *margin*, never font-size. So prose paragraph text renders at the browser default (16px), inheriting Poppins from the root layout, not the app's 13px `text-base` token. **This does not change D-02's decision** — `ch` is a relative unit that self-corrects to whichever font-size is actually in force at the element — but the planner should know the 70ch target resolves against 16px Poppins body text, not 13px, when eyeballing the screenshot diff. Not a blocker; stated so the checker does not flag an unexplained size discrepancy.

### SURF-01 contract — the actual deliverable of this section

**`::selection` (D-04, alpha resolved by this document per Claude's Discretion):**

```css
::selection {
  background-color: hsl(var(--accent) / 0.3);
}
```

- Alpha locked at **0.3** (not the "~0.3, tune it" placeholder `11-CONTEXT.md` left open). Rationale: 0.3 is heavy enough to read as an intentional brand wash against both the light page background (`#faf8f5`-family) and the dark background (near-black), and light enough that the selected text's own inherited color stays legible underneath — the same alpha the project already uses for other accent washes (`--accent-subtle` is `30 100% 45%/0.15` light, `30 100% 50%/0.2` dark; `nav-item-active` uses `/0.2`; this phase's 0.3 sits one step brighter, appropriate for a transient selection state rather than a persistent UI surface). A single rule (no `:root`/`.dark` duplication) is sufficient because `--accent` already carries separate light/dark values.
- **No explicit `color` override on `::selection`** (resolves the second open discretion item). The selected text keeps its own inherited foreground color; only the background changes. Rationale: avoids introducing a second contrast pairing this workstream would need to measure (Phase 07's contrast rigor doesn't extend to `::selection` foreground by any requirement here), and browsers already render inherited text color correctly over a translucent background by default.
- Verification: confirm visually at the phase's screenshot gate, both themes. If either theme reads illegibly, the fallback is to add `color: hsl(var(--foreground))` to the same rule — a one-line, reversible change — not a re-architecture.

**`caret-color` (D-05, locked, not discretion):**

```css
html {
  scrollbar-gutter: stable;
  caret-color: hsl(var(--accent));
}
```

Extends the existing `html` rule at `app/globals.css:317-319` (confirmed live) rather than adding a new selector — `caret-color` is inherited, so setting it once at `html` themes every text input, textarea, and contenteditable region app-wide with zero per-component changes. Same value both themes via the existing `--accent` token pair.

**Content-area scrollbars (D-06, D-07 — mechanism resolved by this document per Claude's Discretion):**

```css
@layer base {
  /* ...existing html/body rules... */

  * {
    scrollbar-width: thin;
    scrollbar-color: hsl(var(--border)) transparent;
  }

  *::-webkit-scrollbar {
    width: 6px;
    height: 6px;
  }

  *::-webkit-scrollbar-track {
    background: transparent;
  }

  *::-webkit-scrollbar-thumb {
    background: hsl(var(--border));
    border-radius: 3px;
  }

  *::-webkit-scrollbar-thumb:hover {
    background: hsl(var(--border-strong));
  }
}
```

- Mechanism resolved as a **universal selector inside the existing `@layer base` block** (not a `body`-only rule, not a new utility class). Rationale: D-06 requires "every scrollable region... not only the page-level vertical scroll" — a universal selector is the only mechanism that covers main content, modals, dropdowns, and horizontally-scrolling tables without hunting down and class-tagging every scrollable container individually. `scrollbar-width`/`scrollbar-color`/`::-webkit-scrollbar*` only have visible effect on elements that actually overflow-scroll, so the universal selector is inert (and cheap) everywhere else.
- Values copied verbatim from `.sidebar-scrollable` (`app/globals.css:367-390`, confirmed live) per D-07 — `--border` thumb, transparent track, `--border-strong` hover. **One addition beyond the sidebar's exact rule:** `height: 6px` alongside the existing `width: 6px`, since D-06 explicitly names "horizontally-scrolling tables" as in scope, and the sidebar's own rule (vertical-only) never needed a height value.
- **Consequence for the planner, named explicitly:** once this ships, `.sidebar-scrollable`'s four rules (`app/globals.css:367-390`) become redundant — byte-identical in effect to the new universal rule. Deleting them is optional (zero visual difference either way, since the universal rule already covers the sidebar); leaving them is also correct (harmless duplicate specificity, same values). This document does not force a choice — record whichever the planner picks at the checkpoint, but do not present it as a visual decision, because it is not one.

### Above-the-fold risk — explicit, per ROADMAP's own risk note

**The wrapper being narrowed is not just the prose body — it is the same `<div>` that also contains each page's breadcrumb, H1, and intro paragraph** (confirmed live: `app/blog/dkp-is-dead-what-classic-guilds-use-in-2026/page.tsx:122-156` opens the wrapper, then nests the breadcrumb (124), the `<header>` with H1 and intro `<p>` (136-153), *and* the prose content div (156) all inside that one wrapper). Narrowing the wrapper from 768px/896px down to `70ch` (≈490-620px depending on rendered font metrics — verify visually, do not treat as exact) can cause the H1 or intro paragraph to wrap onto an additional line, which pushes everything below it down by that many line-heights. This is exactly the re-flow the ROADMAP risk note warns about, and it is not confined to deep-scroll content — it starts at the very top of the wrapper, in the part of the page most likely to be above the fold.

**Required at the plan/execution checkpoint (not optional, not a courtesy):**
1. Screenshot the **full page** (not just the prose block) at 1440 and 390, both themes, before and after, for all four page types: one representative blog post, `research`, `compare`, and `pricing`.
2. Name explicitly, by page and by element, anything that moves from above-the-fold to below-the-fold as a result of the narrower wrapper (most likely candidate: the H1/intro-paragraph area on blog posts and research, since those have the longest headline+byline block before the fold; least likely: `pricing`'s FAQ, since D-03 applies the measure only to the `<p>` deep in the page, not to a page-opening wrapper).
3. Do not silently absorb any such shift as "intended" — per Phase 09's D-05 precedent (cited in `11-CONTEXT.md`'s canonical refs), route it forward by name to whoever owns the sprint's conversion-cohort measurement, the same posture already established for cramped/clipped/wrapped findings in this workstream.
