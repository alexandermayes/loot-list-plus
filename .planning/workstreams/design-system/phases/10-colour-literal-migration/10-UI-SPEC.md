# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase shape note:** This phase is almost entirely a mechanical token/literal rename (COLOR-03, COLOR-04, COLOR-05) with one bounded visual-judgment area (COLOR-07's 6 purple/gradient sites). Every value below traces to a locked decision in `10-CONTEXT.md` (cited by ID) or to a value already live in `app/globals.css` / `tailwind.config.js`. Nothing in this document introduces a new token, a new hex value, or a new visual language — that would contradict D-01 through D-14's own stated pattern ("prefer the existing semantic token over a new one").

### This phase's actual token contract (COLOR-03/04/05, not a 60/30/10 palette change)

The 60/30/10 table above is the app's existing palette (unchanged). This phase's real color work is four narrow, already-decided substitutions:

**A. `--background-inset` deletion (D-06, D-07, D-08)**

| Current site type | Count | Replacement | Exact class/token |
|---|---|---|---|
| Card-shaped (border + radius, nested inside another card) | 6 sites (`ProfileContent.tsx:908`, `DashboardContent.tsx:2239`/`:2411`, `EditCharacterModal.tsx:405`, `skeletons.tsx:69`/`:133`) | `<Card variant="nested">` | Phase 09's existing `nested` variant — border-t divider only, `first:border-t-0`, no new fill/border/radius token |
| Non-card (progress-bar track, pill, bordered chip, hover swap) | 6 sites (`DashboardContent.tsx:2088`/`:2167`, `LootListSummaryView.tsx:206`/`:224`/`:235`, `horizontal-scroll.tsx:68`) | `--muted` / `hover:bg-muted` | `bg-muted` (light `35 15% 90%`, dark `0 0% 16%`) uniformly across progress track, pill, chip-with-border, and hover swap — one token, not four (D-06) |
| `--background-inset` itself | n/a | deleted | Removed from `app/globals.css` `:root` (line ~136) and `.dark` (line ~224), and from any `tailwind.config.js` `background.inset` reference (D-08) |

Live re-inventory in CONTEXT.md found a 7/5 card/non-card split (not 6/6); the planner re-measures at plan time per the workstream's established convention — this table reflects the CONTEXT.md baseline, not a re-litigated split.

**B. Faction colour fidelity (D-09, D-10, D-11)** — `GuildSettingsContent.tsx` lines ~560-611

| Element | Current (hardcoded) | Replacement | Visual weight preserved |
|---|---|---|---|
| Selected-state border | `border-blue-500` / `border-red-500` | `border-alliance` / `border-horde` | Full-token-color border, unchanged |
| Selected-state fill | `bg-blue-500/20` / `bg-red-500/20` | `bg-alliance/20` / `bg-horde/20` | Same `/20` opacity, unchanged |
| Label text (selected + hover) | `text-blue-400` / `text-red-400` (no token equivalent) | `text-alliance` / `text-horde` | D-11: accepted as a small, barely-noticeable darkening — reuses the single existing token rather than adding `--alliance-light`/`--horde-light`. If this reads poorly in the screenshot gate, it is explicitly revisitable (reversible) per D-11, not a hard commit. |
| Hover-glow `<style jsx>` block | Raw `rgba(59,130,246,…)` / `rgba(239,68,68,…)` in `box-shadow`/`background` | `hsl(var(--alliance))` / `hsl(var(--horde))` | Identical glow effect (same shadow spread, same opacity stops); only the color source changes from a hardcoded rgba triplet to the CSS custom property. The `<style jsx>` block itself is not removed (D-10). |

`--alliance` (`217 91% 60%`) and `--horde` (`0 84% 60%`) already exist (Phase 07) and are byte-identical to the `blue-500`/`red-500` values they replace — this is provably a rename, not a re-color.

**C. WoW item-quality / brand colour centralization (D-12, D-13, D-14)**

Not a CSS-variable token (unlike A/B above) — these 5 hex values are consumed as JS/TS data (conditional style objects, a hex-keyed CSS `filter` lookup in `AccentColorContext.tsx`), so D-12 locks a shared TypeScript constants module as the mechanism, not `globals.css`/`tailwind.config.js`.

| Constant name (D-13) | Hex (preserved verbatim) | Current raw-literal sites found live |
|---|---|---|
| `QUALITY_COLORS.epic` | `#a335ee` | `RaidCardHeader.tsx:109`, `WeekGroup.tsx:65`, `KonamiEasterEgg.tsx` (x4), `ItemLink.tsx:116` |
| `QUALITY_COLORS.legendary` (name pending D-13 reconciliation — see below) | `#1eff00` | `PremiumItemTooltip.tsx` (x5) |
| `BRAND_COLORS.battlenet` | `#0074E0` | `ProfileContent.tsx:637`, `characters/[id]/edit/_client.tsx:576`, `EditCharacterModal.tsx:457`, `CreateCharacterModal.tsx:369` |
| `BRAND_COLORS.discord` | `#5865F2` | `RaidCardHeader.tsx:154`, `lib/design-system/tokens.ts:81` (already a named `500` shade — natural re-export point), `design-system/_client.tsx:329` (docs only) |
| `BRAND_COLORS.wcl` | `#e35e15` | `RaidCardHeader.tsx:119`, `AttendanceContent.tsx:1248` |

**Reconciliation flag carried into this contract (D-13, unresolved by CONTEXT.md, explicitly left to the planner):** `AccentColorContext.tsx`'s own `ACCENT_COLORS` array — the *user-selectable app accent color* picker, a different feature from the quality/brand literals above — already has an entry named `'Uncommon'` at `#15b300`, described in its own comment as "darkened from `#1eff00`". The literal `#1eff00` this phase must centralize is spelled verbatim only in `PremiumItemTooltip.tsx` (5 sites) and in `landing/ClickEffects.tsx` / `landing/ParallaxItem.tsx` (landing, likely out of this phase's `app/`+`components/` scope per D-05's spirit, but not explicitly named — planner to confirm). **Do not assume `#1eff00` is "Uncommon"**: WoW Classic's actual quality tier at bright green (`#1eff00`) is **Legendary** in the retail palette but **Uncommon (green)** in Classic's tier ladder — `AccentColorContext.tsx` calls its own darkened green "Uncommon," which is the Classic-correct tier name. The planner must pick one of: (a) name the new constant `quality-uncommon` to match Classic convention and `AccentColorContext.tsx`'s existing precedent, or (b) verify against the 34-occurrence grep which visual context `#1eff00` renders in (`PremiumItemTooltip.tsx`'s "Legendary"-labeled copy, per its filename/adjacent JSX, would argue for `quality-legendary` instead). This UI-SPEC does not resolve it — CONTEXT.md's own Claude's Discretion section defers it explicitly — but flags it so the checker does not silently accept a mis-tokenized name.

Full item-quality tiers beyond these 5 (Poor/gray, Common/white, Rare/blue, Artifact/gold) are explicitly NOT in scope (D-14) — do not expand the constants module beyond the named 5 unless a genuine additional literal-spelling site is found.
