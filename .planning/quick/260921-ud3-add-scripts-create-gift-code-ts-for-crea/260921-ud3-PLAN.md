<objective>
Add a reusable repo script that mints a single-use, expiring, 100%-off Stripe promotion code an operator can hand to a guild as Premium for free.

Purpose: gifting Premium today has no safe path. Doing it by hand in the Stripe dashboard is a live-mode, 100%-off, multi-step operation with no guardrails and no audit trail. This script makes the safe version the easy version: it defaults to single-use and expiring, refuses to touch live mode without an explicit confirmation, tags what it creates as a gift, and never lets the secret key reach the terminal.

Output: `scripts/lib/gift-code.ts` (pure helpers, unit tested), `scripts/create-gift-code.ts` (the CLI), and a `gift:code` alias in `package.json`.

Scope boundary (D-01): the gift mechanism is a Stripe promotion code and nothing else. No schema change, no API route, no UI, no product feature, and no edit to any existing billing file. `app/api/billing/checkout/route.ts:79` already sends `allow_promotion_codes: true`, and `app/api/webhooks/stripe/route.ts` already flips `guilds.subscription_tier` to `'pro'` when the resulting subscription goes active - both stay untouched. The only existing file this plan modifies is `package.json`.

<planner_decisions>
Judgment calls the requirements left open, decided here with rationale. The executor implements these as written.

**PD-1 - Live-mode confirmation accepts both a prompt and a flag.** When the key starts with `sk_live_`: if `--yes` was passed, proceed; else if `process.stdin.isTTY`, print the loud warning and read a line from stdin, proceeding only on exactly `yes`; else (piped, CI, agent-driven) exit non-zero telling the operator to pass `--yes`. Rationale: a stdin prompt is the friendlier interactive experience, but a prompt-only design either hangs or silently auto-proceeds when stdin is not a terminal - which is exactly the situation where an accidental live 100%-off code is most likely. Refusing the non-interactive live run without `--yes` makes the dangerous default a hard stop rather than a hang. A test-mode key skips the gate entirely.

**PD-2 - Code format: `GIFT` + 8 characters from a 30-character unambiguous uppercase alphabet.** Alphabet `23456789ABCDEFGHJKMNPQRSTVWXYZ` - the digits and letters that survive being read aloud over Discord voice or retyped from a screenshot, with `0/O`, `1/I/L` and `U` removed (Crockford's exclusions). 8 characters gives roughly 39 bits of entropy, drawn with `crypto.randomInt` for unbiased selection. No separator character: the code is restricted to `[A-Z0-9]` so there is zero risk of Stripe rejecting a punctuation character, and Stripe uppercases promotion codes anyway. An operator-supplied `--code` is uppercased and must match `/^[A-Z0-9]{4,40}$/`; this is deliberately stricter than Stripe, because rejecting locally with a clear message beats a round-trip API error and a possible orphaned coupon.

**PD-3 - Yes, check the code is not already taken, before creating the coupon.** `promotionCodes.list({ code, limit: 1 })` first. Rationale: Stripe enforces promotion-code uniqueness only among *active* codes, so a collision either fails the second create (leaving behind an already-created, orphaned 100%-off coupon) or succeeds into an ambiguous pair. One cheap read removes both outcomes. The check is skipped in `--dry-run`, which makes no network calls at all.

**PD-4 - Two files, not one.** The pure logic lives in `scripts/lib/gift-code.ts` with no dotenv call, no Stripe client construction, and no top-level side effects, so the test file can import it without loading `.env.local` or risking a stray API call. Putting the helpers in the CLI file instead would require an execution guard, and `import.meta.url` is unavailable because tsx runs these `.ts` files as CommonJS (no `"type": "module"` in package.json).

**PD-5 - The script constructs its own `new Stripe(key)` rather than importing `getStripe()` from `lib/billing/stripe.ts`.** Two reasons: no script in `scripts/` uses the `@/` path alias, so alias resolution under tsx is unproven in this repo; and `getStripe()` returns `null` when the key is unset, which is the right behavior for a route that must degrade to a 503 but the wrong behavior for a CLI that must fail loudly. The env var name is identical, so the two stay in sync by contract.

**PD-6 - Tests: yes for the pure helpers, never for the Stripe calls.** The pure parts are exactly `expect(fn(input)).toBe(output)` shaped and each guards a real failure this script is uniquely able to cause: a wrong `expires_at` silently mints a code that never expires, a missing `max_redemptions` mints an infinitely reusable 100%-off code, and a redaction miss leaks key characters into a terminal or a pasted log. Those are cheap to test and expensive to get wrong, so they get tested. The Stripe calls themselves get no test: mocking the SDK would assert only that the mock was called, and hitting the API from the suite is off the table. `scripts/` is covered by `tsconfig.json`'s `**/*.ts` include, so `npm run typecheck` already type-checks both new files against the real Stripe param types - the compiler proves the payload shapes that a mock would only pretend to.

**PD-7 - No top-level `await`.** package.json has no `"type": "module"`, so tsx executes these files as CommonJS. Follow `scripts/seed-test-data.ts`: an `async function main()` invoked as `main().then(...).catch(...)` at the bottom.
</planner_decisions>

<flagged_out_of_scope>
Findings that touch files outside this plan's scope. Recorded, deliberately not acted on.

1. **The recipient will still be asked for a card, even at a zero total.** `app/api/billing/checkout/route.ts` does not set `payment_method_collection`, and Stripe's default is `always` - Checkout collects a payment method even when the amount due is 0. A 100%-off gift therefore reaches a card form. Making the gift truly card-free would mean setting `payment_method_collection: 'if_required'` on that route, which would also change behavior for every trial signup, not just gifts. That is an app-code change, explicitly out of scope per D-01 and the plan constraints. Flagged for a separate decision.

2. **Trial stacking is harmless but worth knowing.** The same route grants a 14-day trial to guilds that have never subscribed. A trial-eligible guild redeeming a forever 100%-off code gets the trial first and then an indefinitely discounted subscription. No change needed; the webhook flips `subscription_tier` to `'pro'` on activation either way.

3. **No revoke path.** Deactivating a gift is a dashboard action. If gifting becomes routine, a companion `scripts/revoke-gift-code.ts` is the natural follow-up; not planned here.
</flagged_out_of_scope>
