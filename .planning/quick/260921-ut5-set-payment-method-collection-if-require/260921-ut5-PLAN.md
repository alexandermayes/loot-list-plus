<objective>
Stop the Premium Checkout Session from demanding a card when nothing is due today, and make a trial that ends without a card pause instead of invoicing.

Purpose: a guild redeeming a 100%-off gift code today is still shown a card-number field, because Stripe's `payment_method_collection` defaults to `'always'` and the route never overrides it. Asking for a card to pay $0 is the single most obvious friction point on the gift path shipped in the previous quick task. Setting `'if_required'` removes it. The paired `trial_settings` change is the deliberate consequence-handler: once cards are optional, a normal 14-day trial can reach day 15 with no payment method, and `'pause'` is the chosen end behavior for that case.

Output: two fields added to one `stripe.checkout.sessions.create` call in `app/api/billing/checkout/route.ts`, with the comments that explain them.

Accepted consequence (locked, not a regression to design around): normal 14-day trial signups will no longer leave a card on file and will pause at trial end instead of converting automatically. The user confirmed this is the intended behavior.

Scope boundary: `app/api/billing/checkout/route.ts` is the ONLY file this plan modifies. `lib/billing/tier.ts` needs no change - `tierForStatus` already returns `'free'` for `'paused'` via its `default` branch, and `lib/billing/__tests__/tier.test.ts:16` already asserts it. The Stripe webhook, `lib/billing/sync.ts`, the database schema, and the gift-code CLI from quick task 260921-ud3 all stay untouched.

Tracer-first decomposition is a no-op here and is deliberately not applied: there is exactly one path (browser -> route -> Stripe -> webhook -> tier), every layer of it except the route already exists and is shipped, and the change touches one file. There is no architecture to prove end-to-end and nothing to expand out from, so the plan is the change plus its gate rather than a tracer plus expansion tasks.
</objective>

<test_strategy_decision>
The constraint asked for a reasoned decision on adding a route-level test. **Decision: no new test.** `app/api/billing/checkout/route.ts` keeps its current state of having no test file. Rationale, in order of weight:

1. **The strongest available automated gate already exists and already runs.** The only mechanically checkable risk in this change is a wrong param shape or a misspelled key. `npm run typecheck` runs `tsc --noEmit` against `stripe@22.5.0`'s own bundled type definitions, which declare `payment_method_collection?: 'always' | 'if_required'` at the session-params top level and `trial_settings: { end_behavior: { missing_payment_method: 'cancel' | 'create_invoice' | 'pause' } }` with both inner keys required. A wrong nesting, a typo, or a value outside the union is a hard compile error. This exact class of error was caught by this exact gate once already, in the preceding quick task. A type-level check against the vendor's own declarations is strictly stronger than an assertion against a mock whose shape we would also be authoring.

2. **A route test here would be a tautology against a fake.** With `stripe.checkout.sessions.create` mocked, the only available assertion is that the params object we just wrote contains the keys we just wrote. It cannot answer either question that actually matters - does Stripe's hosted Checkout really skip the card field at $0, and does the subscription really transition to `paused` at trial end. Those need a live test-mode session and a Stripe test clock, and they are captured as human-checks below.

3. **The cheap-mocks alternative would mean refactoring a live payment path.** The repo's own convention for making logic testable without mocks is extraction to a pure module - `lib/billing/tier.ts` is commented "Kept dependency-free so it's trivially unit-testable", and quick task 260921-ud3 extracted `scripts/lib/gift-code.ts` for the same reason. Applying that here would mean lifting the whole session-params object out of a shipped, working, revenue-carrying route into a new builder module, so that a test could assert two literals. That is a refactor of a payment path riding along with a config change, and it carries more risk than the regression it would guard. The precedent does not transfer: 260921-ud3 extracted brand-new code, not shipped billing code.

4. **The genuine residual risk is silent deletion, and it is mitigated in the house style.** The real hazard is a future refactor quietly dropping one of these fields, re-breaking the gift path invisibly. The established mitigation in this very code block is a why-comment: `managed_payments: { enabled: false }` two lines above carries a four-line "Deliberately disabled: ..." rationale for exactly this anti-deletion purpose, and it has survived. Task 1 gives both new fields the same treatment.

5. **Do not add** a test asserting `tierForStatus('paused') === 'free'`. `lib/billing/__tests__/tier.test.ts:16` already covers it.

The automated gate for this plan is therefore `npm run typecheck` + `npm run lint` + a full `npx vitest run` regression sweep, backed by the human-checks in Task 2.
</test_strategy_decision>
